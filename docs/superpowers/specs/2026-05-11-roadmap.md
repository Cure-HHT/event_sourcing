- **CLAUDE.md "Epistemic layers"** section codifies the Layer 1 (cryptographic + structural facts) / Layer 2 (library-provided conventions) split.

### Open design questions deferred from per-task reviews

**Resolved by the 2026-05-11 entry-type-version-substrate-owned design**
(`docs/superpowers/specs/2026-05-11-entry-type-version-substrate-owned-design.md` + plan + implementation):

1. ~~**Does the append path need to invoke promoters?**~~ — Resolved.
   Producers always emit at `registeredVersion` (substrate stamps it; the
   parameter is removed from `EventStore.append`/`appendInTxn`). Live
   append never sees a version mismatch. Ingest transparently promotes
   older-peer events before the fold via `ProjectionInterpreter`.
   `EventStore.open` snapshot-promotes view rows when a
   `registeredVersion` bump leaves `view_target_versions` lagging.
2. ~~**Should `ActionDispatcher.entryTypeVersion` look up the
   registry?**~~ — Resolved by removing the parameter entirely. The
   substrate stamps the version internally; no caller chooses it.
3. ~~**Does `view_target_versions` retain its purpose?**~~ — Resolved:
   YES, with sharper rationale. It's the per-(view, entry-type) marker
   that drives auto-promotion on boot. Snapshot promotion compares
   stored target against `registeredVersion`; equal = no-op,
   lower = promote-then-bump, higher = refused.

## Phase II — multi-source canonicalization

Currently dormant per the "Single-source-per-aggregate-type today" architectural commitment. Activated when a real consumer demands multi-source semantics (typically: when an aggregate needs concurrent contributions from multiple independent installs).

### Planned scope

- **Settings-event-driven registration.** `register_projection(spec)`, `register_promoter(spec)`, `revoke_*` events drive the registries from the log itself, replacing Phase I's composition-time `ProjectionRegistry()..register(...)` pattern. The substrate's bootstrap reads these events from the log before serving subscribers. Closes the spec-set's audit loop (today the spec set is configured at deploy time, not in the log).
- **Multi-source canonicalization rule grammar.** The `MaterializerRules` machine (presently fixed to "originator-of-first-event-is-canonical") extends to load additional rule types from settings events: `set_canonicalizer(aggregateId, ruleSpec)`, `delegate_canonicalization(aggregateId, fromAuthority, toAuthority)`, `revoke_canonicalization_delegation(aggregateId, ...)`. Closed-set discipline; new rule types are library work.
- **Cross-install aggregate-id resolution.** Phase I has a known issue: events keyed by literal `aggregateId='_lib'` from different installs conflate under Phase II ingest. Resolution: aggregate identity probably becomes `(source.identifier, aggregateId)` tuple rather than `aggregateId` alone, allowing each install's `_lib` aggregate to be distinct from a destination's perspective.
- **Approval-pattern event types.** Events approving non-canonical edits flow through the same dispatcher path; the materializer rules consume them per a registered rule. Phase II authors the concrete event types and the materializer-rule semantics.
- **Per-entry-type resolution policies.** A product-side decision more than substrate code; Phase II surfaces hooks for it but doesn't impose a default beyond originator-of-first-event.

### Substrate seams already in place

- `SubscriptionFilter.sources` field exists and is wired through `matches()`, but is functionally unused while the single-source invariant holds. Phase II activates it.
- Hash chains are stored per-authority (a single chain in v1; multiple intersecting chains in Phase II).
- The dispatcher records authority on every event; subscriptions can already filter by authority.
- Phase II does not add new substrate primitives — it populates rules.

## Recent architectural decisions (not yet in PRDs)

These decisions were reached in conversation during the 2026-05-11 session and are not yet codified in dedicated spec docs. They are binding for future sessions unless explicitly revisited.

### `device_announced` pattern (cross-install state sync)

**Problem.** The destination `startDate` gate (per `fill_batch.dart:149` — events with `client_timestamp < startDate` are permanently rejected from outbound shipping) excludes pre-startDate bootstrap events. When a diary connects to a portal that's already running, the portal "misses" the diary's bootstrap events (`lib_version_initialized`, `entry_type_registry_initialized`, `system.destination_*`). The portal therefore can't know the diary's configuration (entry types it supports, software version, user preferences like language/font/retention policy) from the substrate alone.

**Decision.** Introduce an app-level `device_announced` event in the consuming app's vocabulary (specifically hht_diary's `lib/src/events/` or equivalent). The diary emits it at the end of bootstrap, after `setStartDate(...)` returns (so `client_timestamp >= startDate`; ships normally via the standard sync path). Payload includes:

- `installUuid`: the diary's `Source.identifier`
- `softwareVersion`: from `Source.softwareVersion`
- `linkingCode`: the portal-issued linking code (see authentication decision below)
- `registeredEntryTypes`: map of `{<entryTypeId>: <registeredVersion>}` — what entry types the diary knows about
- `preferences`: app-domain dictionary (language, font, retention policy choice, etc.)

**Re-emission policy.** Every boot with `dedupeByContent: true` — same-state reboots collapse to no-ops; only material changes (new preference, new entry type, software upgrade) emit a fresh event.

**Substrate offers no hook.** `device_announced` is purely app-domain; the substrate stays domain-neutral. The library does NOT ship a `kDeviceAnnouncedEntryType` constant or a default fold for it.

**Rejected alternative: substrate-level "replay bootstrap events on native sync establishment."** Reasons:

1. It would conflate the source's `_lib` aggregate with the destination's (Phase I single-source-per-aggregate-type violation; see Phase II cross-install aggregate-id resolution above).
2. It would clutter the destination's log with N installs' worth of substrate bootstrap events without adding real audit value.
3. The substrate's bootstrap events audit the SOURCE's own internal state — they're not configuration intended for the destination to act on. Mixing those concerns conflates audit-of-self with audit-of-peer.
4. The startDate gate exists for a reason (backfill protection, retention alignment). Carving out exceptions for "essential" events undoes its purpose.

### Portal-to-diary linking-code authentication (auth boundary closure sketch)

**Problem.** The Principal-on-faith trust boundary (CLAUDE.md "Trust boundaries"). The portal can't verify which diary install is "actually" announcing as `installUuid=X`. Anyone with the wire-format envelope can claim to be install X.

**Decision (architectural sketch; implementation in hht_diary).** Portal issues a linking code to the diary out-of-band (e.g., human-readable shortcode displayed in the portal's UI, typed into the diary). On first announce, the diary includes the linking code in its `device_announced` payload. The portal binds the linking code → installUuid mapping on that first announce. From then on, ingested events claiming to come from `installUuid=X` are only accepted if their wire-format envelope's authentication signature matches the bound UUID (mechanism TBD; could be a per-install symmetric key derived from the linking code, or a more elaborate keypair).

This closes the authentication boundary for the diary-portal pair specifically. Full closure of the Principal-on-faith boundary (the `AuthenticationProvider` pluggable interface sketched in `TODO-auth-note.md`) is still future work but the linking-code pattern handles the immediate use case for hht_diary.

**Substrate work required:** none for the linking-code pattern itself (it's app-domain) — but the library SHOULD eventually grow an `AuthenticationProvider` interface that lets the linking-code logic plug into the substrate's standard trust-boundary set rather than living entirely in app code.

### Phase I matching-entryTypes requirement

Both the diary and the portal must register the same `entryTypes:` list in `bootstrapAppendOnlyDatastore` for Phase I deployments. Phase II's multi-source work would relax this with entry-type registry events that propagate via ingest, but that's not yet built.

In practice for hht_diary: both panes are built from the same Dart codebase, so the same constants drive both. Not a real friction point today. Documented for future awareness.

### Layer 1 facts vs Layer 2 conventions (charter Assertion I)

The library distinguishes substrate guarantees (cryptographic and structural facts about the event log) from library-provided conventions (default interpretations such as tombstone-as-row-deletion, null-as-clear merge, originator-of-first-event canonicality). See CLAUDE.md "Epistemic layers" for the full framing.

**Authoring discipline going forward:** when authoring new surfaces, distinguish in identifiers AND doc comments between Layer 1 facts (use absolute language: "SHALL preserve hash-chain integrity") and Layer 2 conventions (use convention-naming language: "the default `AggregateProjectionSpec` interpretation TREATS event types in `tombstoneEventTypes` as row deletions"). Ongoing audit of existing surfaces (especially `EVS-PRD-materializer` and `EVS-PRD-permissions-as-events` absolute language) is governed by Assertion I; do it opportunistically when those files are next touched.

### Survey-example architectural insight

Discussed in conversation but not formally captured: a clinical survey scenario illustrates the substrate's epistemic honesty. The substrate provides a tamper-evident, attributed stream of statements of fact (event 1: participant submits, event 2: clinician corrects). The substrate's default projection (Layer 2) materializes these via generic merge (last-write-wins). The analyst may want a different view ("for FDA submission, only count first-submission by participant"). That's a Layer 2 alternative; built on top of `subscribe<T>(_, Events())` or `EventStore.read(...)`, not inside the substrate's projection model.

This is the canonical example for why Assertion I matters: the substrate provides facts; apps provide interpretations. Tombstoning, completeness, finalizing — these are business-logic conventions, not substrate guarantees.

## Backend portability (deferred; no committed timing)

The substrate is built against an abstract `StorageBackend` interface, with
`SembastBackend` shipped as the in-lib reference implementation. The portal
side of `cure-hht` already runs on a SQL backend implemented outside this
lib. No fundamental obstacle blocks a SQL `StorageBackend` impl: the
substrate's API is SQL-friendly (transactional via abstract `Txn`,
JSON-shaped variable payloads in `data`/`metadata`, integer sequence
numbers, simple hash strings stored as columns).

The one architectural decision that has substrate-API impact and is worth
deliberation when this work activates: **view-row representation on SQL
backends.** Today every backend stores view rows as opaque
`Map<String, Object?>` records. On a SQL backend, app code could
alternatively read view rows as native typed columns (with `SELECT` /
`JOIN` / `GROUP BY` querying directly against the view). That richer
integration affects whether the substrate or the backend owns view-table
schema migration when `ProjectionSpec`s change, and whether `derivedFields`
declare themselves in a typed-column world. The decision can be deferred
until a concrete consumer requires it.

Activation triggers (any of these would justify picking this up):

- The portal's existing SQL backend wants to be lifted into this lib as a
  second reference implementation.
- `hht_diary` adoption surfaces a backend-swap need (e.g., performance
  characteristics of sembast hit a wall on a real dataset).
- A new consumer requires native SQL access to materialized views.

Until one of these triggers, the substrate stays on the abstract
`StorageBackend` interface with sembast as the only in-lib impl. The
historical reason for the sembast choice on mobile (vs SQLite) is
inherited from the kick-start `hht_diary` codebase; it is not an
architectural commitment.

## Authoring discipline going forward

- **`EVS-DEV-*` requirements** land alongside code per CLAUDE.md "Requirement traceability." ~356 stale `// Implements: REQ-d{NNNNN}` annotations from the kick-start commit remain in production code and need rebinding to `EVS-DEV-*` IDs as code is touched.
- **Assertion I compliance:** when authoring new surfaces, distinguish in identifiers and doc comments between Layer 1 facts and Layer 2 conventions. Apply opportunistically to existing surfaces during routine touches; a dedicated sweep is not necessary.
- **Append-Only Primitives discipline:** library primitives (transformations, derivations, projection shapes, etc.) are append-only. Once shipped with given semantics, they're frozen; bug fixes ship as new primitive names. New behaviour is always a new primitive, never a re-interpretation of an existing one.
- **Greenfield discipline during CUR-1317 libify:** prefer clean designs over backwards-compat scaffolding. This applies while the lib is pre-shipping. Post-shipping discipline shifts to normal SemVer + deprecation.
- **Tests follow code, not the other way around:** when code shape changes, tests get rewritten against the new shape, not duplicated. This is the greenfield-discipline corollary.
