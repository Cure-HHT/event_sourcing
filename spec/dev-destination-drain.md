# EVS-DEV-destination-drain: Destination queue mechanics

**Level**: DEV | **Status**: Active | **Implements**: -
**Refines**: EVS-PRD-destinations

## Purpose

This requirement holds the implementation mechanics of a destination's queue: how queue items change status, how the drainer records its attempts, how the fill enqueues items (including the replays that a registry operation requests), how the drainer records a wedge, how an operator recovers a wedged head, how a destination is deleted and registered again, how an operator's halt request is recorded and how the drainer honours it, which destinations a delivery cycle serves, which reserved system events the library alone appends and how ingest checks them, and how the library registers its reserved entry types and its default destination-wedges view. A wedged head is a queue head whose status is wedged: the drainer stopped at it and delivery on that destination waits for an operator recovery. An operator halt is a request that the drainer honours by wedging the head, with cause operator halt.

## Assertions

A. Deleting a destination SHALL read the queue head inside the deletion's transaction, refuse a pending head, tombstone a wedged head, delete the pending items behind it, remove every per-destination record the library keeps (the fill position, the schedule, the replay request, the wedge record, the halt request and the send fence), and retain the terminal items and the queue-sequence counter; registering a destination SHALL write its hard-delete opt-in as the opt-in in effect, and a deletion SHALL act on, and record, the opt-in in effect; the registry's date, recovery and deletion operations SHALL act on persisted state, SHALL need no destination registered in the calling process, and SHALL refuse an unknown destination with nothing written but the database-wide check record.

B. The library SHALL change a queue item's status only from pending to sent, from pending to wedged, and from wedged to tombstoned.

C. The drainer SHALL commit each delivery attempt in one transaction with the status the attempt produces, or, when the transaction that would mark the head wedged does not commit, the attempt alone.

D. The drainer SHALL record an attempt only on the pending head it sent and SHALL append a wedge event only for the pending head it wedges, and the storage layer SHALL refuse to record an attempt on a missing or terminal item.

E. Only the drainer's fill SHALL enqueue queue items: a registry operation that widens a destination's window SHALL record a replay request that the next fill performs with the destination the draining process registers; a gap replay SHALL enqueue only events at or below the fill position, and the fill only events above it; the library SHALL refuse to move a start date earlier while the queue head is wedged; and delivery SHALL fill and send only the destinations registered in the draining process.

F. An operator recovery SHALL read the queue head, remove the trail items, rewind the fill position and remove the destination's wedge record in one transaction.

G. A fill SHALL write queue items, the fill position or a cleared replay request only when, inside its transaction, the persisted schedule (start date, end date, registration and hard-delete opt-in), the head status, the fill position and the replay request equal those its batch was computed from, and SHALL run the destination's transform and every walk of the log outside that transaction.

H. The library SHALL append each kind of destination audit event with one event type, distinct from the event type of every other kind of destination audit event.

I. In the transaction that wedges a queue head, the drainer SHALL write the destination's wedge record, naming the item, the wedge event, the cause and the purpose of the halt request the wedge consumed, and SHALL append a wedge event whose data carries exactly these keys: `id` (the destination); `row_id`, `event_ids`, `first_seq`, `last_seq`, `sequence_in_queue`, `wire_format` and `transform_version` (from the queue item); `cause`; `attempt_count` (the attempts recorded on the item, the final one included; null for an operator halt); `max_attempts` (the retry budget in effect; null when the draining process does not register the destination, where no budget is in effect); `last_outcome` (the outcome category of the last recorded attempt; null for an operator halt); `http_status` (the numeric status a transient last outcome reported, otherwise null); `database_id` (the identity of the database whose drainer appends the event); `halt_request_event_id`, `halt_requested_by` and `halt_purpose` (the identifier of the halt request event the wedge consumed, and the initiator and purpose that event records; each null when the wedge consumed no request); and the reserved keys `drainer_epoch`, `configuration_fingerprint` and `configuration`, each null.

J. An attempt that reports a permanent failure or spends the retry budget SHALL commit with the wedged status, the wedge event and the wedge record in one transaction, or, when that transaction does not commit, alone in its own transaction; before any halt honour, backoff check or send on a pending head, the drainer SHALL give the head the status its recorded attempts call for, wedging it without a further send when its last attempt reported a permanent failure or, where a retry budget is in effect, its attempt count has reached that budget; and the delivery cycle SHALL refuse a retry budget below one, sending nothing under it.

K. Every destination audit event the library appends SHALL carry the identity of the database that appends it, and destination identifiers and database identities SHALL be non-empty and exclude `|`.

L. The event store's public append operations SHALL refuse every reserved system entry type; the library SHALL change the aggregate type and event types it declares for a reserved entry type, or the values of an enumerated field of a reserved event (the wedge cause and the halt purpose), only with a data-format major step; and ingest SHALL refuse, with a named reason and before any write, an event of a reserved entry type whose aggregate type or event type is not one the library declares for that entry type, an event of a reserved destination audit entry type whose destination identifier or database identity is missing, empty, not a string or contains `|`, and an event of a reserved destination audit entry type that names the receiver's own database and that the receiver does not already hold.

M. Opening an event store SHALL register the reserved system entry types and the library's default destination-wedges view, refusing a registry that holds a reserved entry-type identifier or the view's name under any definition but the library's own; and the library's default destination-wedges view SHALL KEY its rows by the database identity the event names together with the destination identifier.

N. Only the drainer SHALL mark a queue item wedged; the drainer SHALL honour an open halt request after the status derivation and before the backoff check, in a transaction that reads and clears the stored request and verifies that the log holds the halt request event it cites for the destination and the database; immediately before each send the drainer SHALL run a fence transaction that writes, and SHALL start the send only when that transaction finds no open request and the queue head unchanged since the payload was built; and, apart from removing a stored request that cites no halt request event the log holds for the destination and the database, the library SHALL write and clear the stored halt request only in the transaction that appends the event that opens or closes the request.

O. A wedge of any cause SHALL consume the open halt request of its destination, removing the stored request and recording the request's identifier, requester and purpose.

P. Among the events the library appends for its own database, every wedge, cancellation or deletion that closes a halt request SHALL name the request event it closes, and the library SHALL append a halt request only while no request is open for that destination.

Q. The library SHALL refuse a halt request for an unknown destination, while another request is open for the destination, or while its queue head is wedged; SHALL accept a halt request on an empty queue and keep it open until the drainer honours it at a head, or a cancellation or a deletion closes it; SHALL refuse a cancellation when no request is open and otherwise close the open request; and SHALL append a halt request event whose data carries exactly `id`, `database_id` and `purpose` (`pause` or `reconfigure`), and a cancellation event whose data carries exactly `id`, `database_id` and `halt_request_event_id` (the request it closes).

R. Deleting a destination SHALL close its open halt request and name it in the deletion event.

T. The delivery cycle SHALL honour halt requests for every persisted destination, including one its process does not register, SHALL fill and send no destination its process does not register and no registered destination whose schedule is no longer persisted, and SHALL report each of them; each pass SHALL decide the destinations it fills and sends and those on which it only honours a halt from one reading of the persisted schedules, so that no destination is both, and SHALL honour a halt on no destination its process does not register when that reading fails; the registry's halt and cancel operations SHALL act on persisted state and SHALL need no destination registered in the calling process; and every registry operation that commits SHALL invoke its event store's delivery-cycle trigger, when one is configured, after the commit.

U. Every destination-registry operation SHALL decide its outcome, refusals and outcomes that change nothing included, inside one transaction that writes, so that on every backend the decision reflects every commit the storage orders before it; an outcome that changes nothing else SHALL write only a database-wide check record.

## Rationale

**Why refuse to delete a pending head, and retain terminal items (assertion A)?** A pending head may be in delivery in the process that drains: that process sends outside any transaction, and a deletion running elsewhere cannot see the send. Deleting the item would lose the record of a delivery the receiver may have accepted, and the drainer's outcome would then find no item to record it on. A wedged head is never in delivery, because only the drainer wedges an item and it does so after its own send returned. So a deletion waits for the wedge, tombstones the wedged head and deletes only the pending items behind it. Items that were delivered, wedged or recovered are the destination's delivery record; they are kept for the database's lifetime, and the queue-sequence counter is kept with them so that items enqueued after the destination is registered again continue above the retained ones instead of colliding with their keys. Every other per-destination record is removed, so a destination registered again under the same identifier starts a new registration with no fill position, schedule, replay request or wedge record inherited from the old one; its refill may send again events the old registration's delivered items carried, which is at-least-once delivery.

**Why the latest registration's opt-in (assertion A)?** The hard-delete opt-in is part of a destination's code, so two releases of one application can register the same destination with different opt-ins while both run during a rollout. Refusing a registration whose opt-in differs from the persisted one would fail the new release's start; the latest registration therefore writes its opt-in as the one in effect, and the registration event records it, so the log's latest registration event for a destination always states the opt-in a deletion acts on. A deletion reads the opt-in from the persisted schedule rather than from a destination object, which is what lets a process that does not register the destination (because the destination was removed from its code) delete it.

**Why act on persisted state (assertion A)?** A destination's delivery configuration is code and lives in the process that drains; its schedule, queue and fill position live in the database. Operators and other processes change a destination's dates, recover its queue or delete it by writing persisted state that the drainer acts on at its next pass. An operation that consulted the calling process's own destination objects would refuse a destination registered only elsewhere, and would decide from a copy that another process may have changed.

**Why these status changes only (assertion B)?** Pending to sent and pending to wedged are the drainer's two terminal outcomes. Wedged to tombstoned is how a recovery or a deletion retires a wedged head. There is no path from pending to tombstoned: a pending head may be in delivery, and tombstoning it would race the drainer's outcome. A repeated status is refused as well: with one writer of each transition, a repeat can only come from a defect.

**Why one transaction per attempt and outcome (assertions C and D)?** An attempt recorded without the status it produced, or a status without its attempt, would misstate what happened: a spent retry budget with a pending item, or a wedged item with no failed attempt behind it. Committing both together means a crash between them loses neither alone; the send is then repeated, which is at-least-once delivery. The one exception is a wedge whose transaction does not commit: the attempt then commits alone, because the receiver saw the send, and the next pass wedges the pending item this leaves before any send (assertion J). A recorded permanent refusal is therefore never sent again, and a spent budget is sent again only when the budget in effect has since been raised above the recorded attempt count. A wedge transaction that reports failure may nonetheless have committed, for example when the connection is lost while the commit is acknowledged; the drainer therefore logs the failure and reads the head again before it records the attempt alone, and records nothing when the head is already wedged under its wedge record, because the attempt committed with the wedge. Because no library operation removes or finalizes an item while the drainer attempts it (deletion and recovery refuse a pending head), an attempt on a missing or terminal item can only come from a defect, and the storage layer refuses it instead of tolerating it.

**Why only the drainer enqueues (assertion E)?** A queue item is built by the destination's transform, which is code in the process that drains. If a registry operation built items in the calling process, a process running an older or newer release could enqueue items built by a configuration the drainer does not use. The operation therefore records a replay request, and the drainer's fill performs it with the destination the drainer registers. The gap replay a backward start-date move requests covers only the events the fill has already passed (at or below its fill position) and the fill covers the events above it, so no event is enqueued by both, including an event with an old client timestamp appended after the fill passed the new start date's window. Moving the start date earlier while the head is wedged is refused: nothing is filled behind a wedged head, so the widened window would take effect only through a recovery the operator has not yet run; refusing it makes the operator recover first and widen afterwards, one fixed order instead of two that interleave. For the same reason, a delivery cycle fills and sends only the destinations its own process registers: a destination whose code is not in the draining process cannot be filled or sent there (assertion T).

**Why rewind below every removed item (assertion F)?** A recovery removes the wedged head and the pending items behind it, and one of those items may be a gap replay's item carrying events lower than the head's. Reading the head, sweeping the trail and rewinding the fill position in one transaction, to just below the lowest event any removed item carried, means the next fill evaluates every removed event again against the destination's current filter and schedule. Events carried by delivered items above that point are enqueued and delivered again: delivery is at-least-once. A replay request pending at the recovery survives and is bounded by the rewound position.

**Why compare and set (assertion G)?** The fill reads the schedule, the head, the fill position and the replay request, walks the log and awaits the destination's transform before it writes. Another process may delete, register again, reschedule or recover the destination meanwhile. The fill's transaction re-reads that state and writes nothing when any of it changed, so a fill never enqueues an item for a registration that no longer exists, never moves a fill position backwards, and never admits an event past an end date set while it ran. The head is compared by its status alone: the fill appends behind the head, so a head delivered meanwhile does not change what it may write, while a head wedged meanwhile means nothing may be filled behind it. The transform and the log walk run outside the transaction because a backend may run a transaction body again after a conflict, and consumer code must not run inside a body the storage may repeat without bound.

**Why a distinct event type per kind (assertion H)?** Every destination audit event is appended to one per-install system aggregate under one aggregate type, so the aggregate identifies the install and not the kind of change. A subscription filter that admits reserved system events admits all of them, whatever its entry-type allow-list says, and the library's default `TableProjectionSpec` interpretation chooses between inserting and removing a row by event type. The event type is therefore the field a filter or a projection can use, without a predicate closure, to tell a recovery from a deletion or a registration from a date change.

**Why a wedge event only for the head the drainer wedges (assertion D)?** The wedge event states that the drainer halted delivery at a named item. The transaction that appends it reads the queue head and refuses an item that is not the pending head, so the log never records a wedge of an item that was delivered, already wedged, recovered, deleted, or still waiting behind another item.

**Why these wedge fields (assertion I)?** The fields identify the database whose drainer halted (assertion K), the halted item (its row, the events it carries, their sequence range and its position in the queue), the configuration it was built under (wire format and transform version, both already on the queue item and in the registration audit), the cause, and the evidence for the drainer's decision: how many attempts were recorded, the budget in effect when the drainer decided, and the category and numeric status of the last outcome the delivery implementation reported. That is enough to audit each wedge decision from the log alone: a permanent refusal is a last outcome of `permanent`, and an exhausted budget is an attempt count at or above the recorded budget. No text from an attempt's outcome is recorded; the full diagnostic stays on the item's attempts. A wedge that consumed a halt request (assertion O) records the request's identifier, and the initiator and purpose its event records, so the log reads which request a wedge closed and who asked for it. An operator halt records no attempt fields of its own: the halt is not a delivery decision, and the attempts on the item, if any, stay on the item. When the drainer honours a halt on a destination its process does not register, no retry budget is in effect for it there, so `max_attempts` is null. Every key is present on every wedge, null where it does not apply and on the reserved keys, so a reader or a declarative projection finds one fixed key set. The wedge record written in the same transaction names the destination's open wedge and the purpose of the halt request it consumed, so the library can read it without scanning the log; recovery and deletion remove it in the transactions that end the wedge.

**Why commit the attempt alone when the wedge fails, and derive the status first (assertion J)?** The attempt that wedges an item happened: the receiver saw the send. If the transaction that records the attempt with the wedge fails, dropping the attempt would lose that record and let the next pass send the item again, possibly past a spent budget or to a receiver that refused it permanently. The drainer therefore commits the attempt alone, and every pass starts by deriving the head's status from its recorded attempts and the budget in effect: a recorded permanent refusal, or an attempt count at or above the budget, wedges the head in a transaction of its own, without a send. The same derivation covers a budget lowered since the attempts were recorded, and an attempt recorded alone before a restart: the next drainer wedges the head before it sends anything. A budget below one is refused: under it every pending head would wedge before its first send, and its wedge event would record an exhausted budget with no attempt behind it. The budget comes from application code, statically or through a resolver consulted each cycle, so the library checks it instead of trusting it: a static budget below one is refused when the delivery cycle is built, and a cycle whose resolved budget is below one logs the refusal and fills and drains nothing, since the cycle is started after appends and an append does not fail because a cycle did.

**Why the database identity on every destination audit, and no `|` in an identifier (assertion K)?** Destination identifiers repeat across databases: every install of an application registers the same destinations, and a node that ingests system events from peers holds destination audits from many databases. The identity the first open mints for a database (`EVS-DEV-event-store-open/F`) names the database that appended each audit, so the default destination-wedges view keys its rows by that identity and the destination together, and ingest recognises an audit that claims to come from the receiver itself. The view joins the two with `|`, so an identifier containing `|`, or an empty one, could make two different pairs render the same key; registration refuses both, with nothing written but the registry check record. The same holds for the identity: the library mints it without `|`, and its reserved appends and ingest refuse a destination audit whose identity is empty or contains `|`, so no peer can assert an identity whose key reads as a row of another database, the receiver's own included.

**Why only the library appends reserved events, and ingest checks their shape (assertion L)?** Reserved system events record the library's own operations: a wedge, a recovery, a registration, a redaction, a boot. An application append of one would state an operation that did not happen, and the default destination-wedges view would fold it, so the public append operations refuse every reserved entry type and the library's own emitters append through internal operations that accept only the aggregate type and event types the library declares for each entry type and, for a destination audit, only data ingest admits. Those internal operations are guarded by the analyzer, not refused at run time; an application that calls one is outside the storage precondition (`EVS-PRD-destinations/L`). This is a Layer 1 claim about events the library appended for its own database. The library declares the aggregate type and event types of every reserved entry type (each security-context audit carries its own event type, so no two reserved entry types share a declared pair and the pair identifies the entry type), and the shape of every destination audit (a destination identifier and a database identity, each a non-empty string without `|`), and it never appends an instance outside them. The declared shapes are fixed within a data-format major: ingest admits an event of the receiver's data-format major at any minor (`EVS-DEV-version-compatibility/D`), so a build that added an event type to a reserved entry type, or changed its aggregate type, would have its events refused by the older builds of its own major and would wedge their peers' destinations on a compatible upgrade. Such a change is a data-format major step; a new kind of reserved event is a new reserved entry type, a minor step, which an older build of the same major stores as an entry type it does not register. An instance outside the declared shapes is therefore not an event any library of the receiver's data-format major appended, whoever forwarded it; ingest refuses it with a named reason, and the whole batch with it, before anything is written. An audit naming the receiver's own database that the receiver does not hold is reachable through forgery, through a durability failure of the trusted backend, or through a peer that forwards the receiver's own events back to it after the receiver's database was restored to an earlier point and lost them; the refusal applies in all three cases. The last needs a destination that forwards a database's own events back to that database, and such a destination fails without any restore: an own event the receiver still holds is refused by the existing identity check. Its fix is the destination's filter, which then leaves out the receiver's own events, followed by a recovery of its wedged head. An event the receiver already holds is decided by the existing identity check, and well-formed audits naming other databases are accepted as the peer asserts them. That the default view's key extraction cannot fail on an ingested event follows from these refusals; it is not the reason for them. The fold and a rebuild share the generic interpreter and add no view-specific validation: over a log written outside the library (which `EVS-PRD-destinations/L` excludes), a rebuild of the default view stops at an audit whose key path does not resolve, naming the event, and leaves the view unchanged.

**Why register the reserved types and the default view at open (assertion M)?** The drainer cannot wedge a head, and no registry operation can record its audit, unless the event store registers the destination audit entry types, and the default view exists only if something registers it. Registering both at every open makes them present in every store without a step an application could forget, and makes them part of every instance's data generation. A registry that already holds one of them is accepted only when it holds the library's own definition, the exported object, which is also what an earlier open with the same registries left there; any other definition under a reserved identifier or the view's name would change what the library's own events mean, so it is refused before anything is written. Keying the view by the database identity and the destination is the library's default convention; the `default` prefix of the view's name says so.

**Why the drainer honours the halt, and why a writing fence before each send (assertion N)?** A send runs outside any transaction, so a wedged status written by an operator while a send is in flight would race the send's outcome. Only the drainer wedges an item, after its own send returned, so a wedged item is never in delivery; an operator's halt is therefore a request that the drainer honours by wedging the head itself. The honour comes after the status derivation (a recorded permanent refusal or a spent budget is the stronger cause, and that wedge consumes the request, assertion O) and before the backoff check, so a head waiting out its backoff is halted at once. The drainer reads the stored request outside any transaction only to decide whether to try; the transaction that honours it reads the stored request again and verifies the cited event, because the log is authoritative: a stored request that cites no halt request event of this destination and database is removed without a wedge, and the drainer logs it and continues. A request committed after that read and before the send is caught by the fence: one transaction immediately before the send reads the stored request and the head, and the send starts only when no request is open and the head is still the item, pending, with the attempt count the payload was built from; otherwise the drainer returns to the head read, where an open request is honoured. The fence writes a record every time it lets a send start, so that on a browser database shared by several tabs, which validates a transaction against other tabs' commits only when it writes, a request committed in another tab before the fence commits is seen. The stored request is a working copy of the log, written and cleared in the transaction of the event that opens or closes the request, so the two agree at every commit. The one removal with no event is of a stored request that the log does not hold: no event opened it, so no event closes it.

**Why any wedge consumes the request (assertion O)?** A halt request asks the drainer to stop delivery at the head. A wedge of any cause has done that: the head is wedged and delivery waits for an operator. Leaving the request open would make the next recovery's refill wedge again at once for a request already served, so every wedge closes the open request and records it, and the recovery that follows keys on the purpose the wedge recorded, whatever its cause.

**Why the library maintains the halt-request relation (assertion P)?** Every event that closes a request names it, and a request is appended only while none is open, so a reader of the log pairs each close with its request and finds at most one open request per destination. This is library behaviour, not a Layer 1 fact: the library maintains the relation from its stored working copy, written and cleared in the same transaction as the event that opens or closes the request (assertion N), and the transaction that honours a request checks only that the cited event exists and is a halt request for this destination and database. The relation therefore holds under the precondition of `EVS-PRD-destinations/L`; a working copy that a write outside the library points at an already-closed request is outside it and is not detected. A cancellation or a deletion names the request its working copy records without consulting the log, under the same precondition: the check guards the wedge, which halts delivery, and a close halts nothing. Ingested events naming other databases are not checked against the relation.

**Why these request and cancellation rules (assertion Q)?** An unknown destination has nothing to halt. A second request while one is open would leave two requests for one halt, and a request on a wedged head asks for a halt already in effect; both are refused, so each honoured request closes exactly one open request. A request on an empty queue is accepted and waits: the operator may halt a destination before its next item arrives, and the first head filled afterwards is wedged before any send. A cancellation with nothing open is refused rather than ignored, so the log holds no cancellation that names no request. The halt events carry a fixed set of keys and a closed purpose vocabulary, so that a reader of the log, and ingest on a peer, interpret them without the library that appended them; a new purpose is a data-format major step (assertion L), since a build that does not know it cannot honour it as intended.

**Why deletion closes the request (assertion R)?** A deletion removes every per-destination record, the stored request included; the deletion event names the request it closes, so the log does not leave the request open forever.

**Why serve only registered destinations, and honour halts on all of them (assertion T)?** A destination's delivery configuration is code in the process that drains. A persisted destination that process does not register (registered by another process, or removed from the code) cannot be filled or sent there, and a registered one whose schedule another process deleted must not be filled; the delivery cycle reports both, so an operator can see what the draining process does not serve. Honouring a halt needs no transport, so the cycle still honours halt requests on persisted destinations it does not register: an operator can halt and then delete a destination that was removed from the code. Where no retry budget is in effect, a head whose last attempt was a permanent refusal is still wedged for that refusal before a halt is honoured (assertion J), so the log does not record an operator halt where a delivery failed. Each pass takes the destinations it serves and those it only honours halts on from one reading, so the two never overlap and no destination is sent and halted at once; a pass that cannot read the schedules does not act on an earlier pass's findings, which a registration since then may have made wrong. The halt and cancel operations act on persisted state, like the date, recovery and deletion operations, so any process can run them. A registry operation that commits invokes the delivery-cycle trigger the application configured on its event store, so that a drainer in the same process acts on the change without waiting for another trigger.

**Why decide every registry outcome in a writing transaction (assertion U)?** A browser database shared by several tabs validates a transaction against the other tabs' commits only when the transaction writes; a read-only transaction may read a tab's cached state. A refusal, or an outcome that changes nothing, therefore writes one small database-wide record and returns its outcome, and the operation throws or returns after the commit, so no outcome is decided on stale data. On a serializable server database the write is harmless.
