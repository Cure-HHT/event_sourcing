# EVS-DEV-destination-drain-lock: Delivery cycle mechanics

**Level**: DEV | **Status**: Active | **Implements**: -
**Refines**: EVS-PRD-destinations

## Purpose

This requirement holds the implementation mechanics of the library's delivery cycle -- the process that fills each destination's queue from the event log and drains it through the destination's delivery implementation -- and of the drain lock that lets one delivery cycle drain a database at a time: how each storage backend excludes drainers and within what scope, how a drainer that another has replaced is fenced from committing, how a delivery cycle stands by, takes over, recovers from a lost lock and closes, how the event store's trigger wakes it, how its cadence and heartbeat run, and the test seams through which the library's own tests observe the library's log lines and inject failures into the operations that change a destination's persisted state.

## Assertions

A. Each storage backend SHALL grant the drain lock of a database to one holder at a time within its scope, and SHALL raise the database's drain epoch in a transaction at every acquisition: on Postgres, a session advisory lock whose key derives from the database, the schema and the database identity, held on the backend's verified lock session, whose acquisition verifies the database identity and, through the pool, that the lock session holds the key, with a scope of every process and session on that library database; on Sembast outside the browser, an isolate-local registry keyed by the open database handle, with a scope of one isolate per open database handle; on Sembast in the browser, that registry together with a Web Lock named for the IndexedDB database and the database identity, with a scope of every tab of the origin on that database, requested only while the tab's page is visible. A tab whose page becomes hidden SHALL start no further send, let the outcomes of its sends in flight commit, waiting for them at most one cadence, release the lock and not request it while its page is hidden; a page without a lock manager SHALL refuse every acquisition as a misconfiguration.

B. Every queue-changing transaction of the drainer SHALL first verify inside that transaction that its drain lock is held and current, holding the stored drain epoch against a concurrent change until it commits, and SHALL commit nothing otherwise; after the drainer detects the loss of its lock it SHALL start no further send.

C. A delivery cycle SHALL stand by when it cannot take the drain lock and begin draining when the lock is granted, without a restart; after the loss of its lock it SHALL return to standby and take the lock again; a start whose acquisition fails for a reason other than contention or misconfiguration SHALL stand by and retry, and one refused as a misconfiguration SHALL throw and leave nothing started; an acquisition that fails after it obtained the backend's exclusion primitive SHALL give the primitive up before it reports the failure; closing a cycle SHALL cancel a pending acquisition, release a grant that races the cancellation, wait for its sends in flight and its handling of a loss or of a hand-over, and leave no acquisition running after it returns; a release the cycle initiates SHALL NOT be treated as a loss; and a cycle whose storage backend can no longer take the lock (the backend was fenced or closed, or its database handle cannot commit) SHALL stop, logging why, SHALL release the lock it holds, SHALL report the cause to the application, and SHALL give up its in-isolate registration, so that a later start over the database is not refused as a second cycle. On Postgres every acquisition step SHALL be bounded by the lock session's query timeout, and the lock SHALL be checked on the cycle's timer every cadence.

D. A delivery-cycle trigger SHALL never raise into the operation that fires it; in standby or after close a trigger SHALL do no work; and an event store's trigger slot SHALL be held by its one started, not yet closed delivery cycle, in standby or running.

E. No trigger that arrives during a pass SHALL be lost: the cycle SHALL run one more pass, and a call that arrives during a pass SHALL return once a pass that started after it has finished; every registry operation that commits SHALL trigger the cycle after the commit; the cycle SHALL run a pass at least once per cadence while running, and no error raised on the cadence or the heartbeat path SHALL stop them or escape the cycle; and each pass SHALL begin with a transaction that verifies the lock and writes a heartbeat record; a pass whose start transaction does not commit writes no heartbeat record, and serves the destinations its registry holds (EVS-DEV-destination-drain/T).

F. The library's test seams SHALL have no effect when assertions are disabled.

## Rationale

**Why a lock per backend, and why these scopes (assertion A)?** At most one drainer may commit queue changes for a database (`EVS-PRD-destinations/V`), and only the storage backend knows who else can reach the database. On Postgres every process and session that reaches the library database can drain it, so the lock is a session advisory lock on a key derived from the database, the schema and the database identity, taken on the backend's lock session: the session the backend verified, when it opened, to be one server session reaching the pool's server, database and schema, and on which it holds its generation locks too (`EVS-DEV-postgres-backend/J`). The scope is part of the key, so two library databases in two schemas of one Postgres database have different keys even when one schema's records, the identity included, are a copy of the other's. Taking the key proves nothing on its own: the acquisition confirms on the lock session that the key is granted to that session, that the database it reaches has the identity the event store opened with, and, through the pool, that the pool sees the lock session holding the key, so that a lock session and a pool reaching different servers are refused as a misconfiguration. On Sembast outside the browser the database file is opened by one isolate of one process (the same trusted assumption the generation guard rests on), so the lock is a registry in the isolate keyed by the open database handle; two backends over one handle collide, and two handles on one file are outside what Sembast supports and outside what the lock claims. In the browser the tabs of an origin share one database, each tab in its own isolate, so an isolate registry alone would exclude none of them from another: each tab's acquisition would raise the shared epoch and fence the other tab's outcomes, and the tabs would take turns re-sending each other's heads. The acquisition therefore also takes a Web Lock through the browser's lock manager, after the registry entry and before the epoch raise; its name joins the IndexedDB name and the database identity, so a copy of the database under another name does not share it. Two sembast databases opened over one IndexedDB name in one page are excluded by the Web Lock exactly as two tabs are. The lock follows the visible tab, because a browser throttles the timers of a hidden page and may freeze or discard it: a drainer in a hidden tab would hold the lock while passing rarely or not at all, and the tab the user works in would stand by behind it. A tab whose page becomes hidden (it is hidden, frozen or being unloaded) therefore starts no further send, lets the outcomes of its sends in flight commit -- the lock is still held and current, so they do -- and releases the lock; the release is its own, not a loss. It waits at most one cadence for those sends: a send whose transport hangs (a connection that stalls without being reset) would otherwise keep the lock from the visible tab for as long as it hangs. Once the lock is released the late outcome commits nothing, since every outcome checks the lock first, and the next drainer sends the item again (delivery is at-least-once). While hidden it does not request the lock, and a request pending when the page became hidden is withdrawn, a grant that races the withdrawal being released at once; once the page is visible it requests the lock again, and a start on a hidden page stands by. So a tab the user works in drains, a hidden or suspended tab never blocks it, and while no tab of the origin is visible nothing drains: the events wait in the database and drain as soon as a tab is visible. A page that the browser freezes before its release completes keeps the lock until it is resumed or discarded (the browser releases every lock of a discarded page), and a visible tab stands by until then: a liveness limit, not a safety one. Web Locks exist only in a secure context (HTTPS or localhost); on a page without a lock manager the acquisition is refused as a misconfiguration, so a delivery cycle there fails at start rather than stand by forever. Every acquisition raises the database's drain epoch in a transaction and records the value it stored, so a transaction can tell the current holder from a replaced one (assertion B).

**Why fence every queue-changing transaction (assertion B)?** A drainer can lose its lock without knowing it: its Postgres lock session can be ended while its process runs on, and another drainer takes the lock. Its sends run outside any transaction, so nothing stops a send already on the wire; what the library can stop is its recording anything afterwards. Every transaction of the drainer that changes a queue -- the pass start, the fill, the halt honour, the pre-send fence and every outcome -- therefore reads the stored drain epoch as its first step and commits nothing when it is not the holder's. A loss the drainer detects on its own timer can arrive while the pre-send fence transaction runs, after its check passed; the drain therefore checks once more, after the fence commits and with nothing awaited before the send, and starts no send once a loss was detected. On Postgres the read takes a share lock on the epoch's row: a transaction whose check took hold of the epoch before a new holder's raise commits, and the raise orders after it, so the new holder reads its writes; a transaction whose check comes while the raise is uncommitted waits for it and then fails with a serialization failure, and its re-run reads the new epoch and commits nothing; one that checks after the raise committed reads the new epoch at once. A plain snapshot read would not do, because under serializable isolation it records only a read dependency, which lets a stale holder's transaction commit after the new holder began draining. A send already on the wire when the lock is lost may therefore arrive after the new drainer's sends (a late duplicate): delivery is at-least-once, and `EVS-PRD-destinations/J` excepts its unrecorded outcome.

**Why stand by, and never stop for contention (assertion C)?** A deployment may run a delivery cycle in every process, and processes come and go: a canary starts beside the serving revision, an instance is replaced, a lock session is lost with the network. A cycle that could not take the lock therefore waits and takes over when it is released, and one that lost its lock waits and takes it again, without a restart; a start never fails for contention or for a transient database error, so an instance that boots during a brief database outage does not crash and does not stop for good. A deterministic misconfiguration -- a lock session that does not reach the pool's server -- is refused at start, where it is loud. An acquisition that fails part-way would, if it kept what it had obtained, leave the lock held by nobody who drains; it therefore gives the primitive up first (on Postgres, by unlocking on the lock session or, when that fails, ending the session), so the next attempt finds it free. Closing a cycle cancels its pending acquisition, releases a grant that raced the cancellation, and waits for the sends it started and for its handling of a loss, so that after close returns the cycle opens no lock connection and makes no acquisition. The terminal outcomes are a fenced backend (a conflicting build registered while the instance's lock session was lost), a closed backend, and a database handle that cannot commit (a browser tab whose handle another tab's open compacted past, `EVS-PRD-event-log/E`): none can take the lock again, and a cycle that kept a lock it cannot use would keep every other process or tab from draining, so the cycle releases the lock and stops with one error line rather than retrying without end with its timers armed. It keeps the error as the cause of its stop, where the application reads it (the handle is recovered only by the application reopening its database), and it gives up its in-isolate registration so that a cycle over a reopened backend can start. A request that stands by ends as soon as its backend is closed or its handle is found unable to commit, rather than when the lock is next granted. A defect -- an error, rather than an exception, from an acquisition -- is not retried either: at start it is thrown, and in a background acquisition it stops the cycle.

**Why a trigger that never raises, and one slot per store (assertion D)?** Appends, registry operations, action dispatch and the security-context operations wake the delivery cycle after they commit, so that a drainer in the same process acts on the change at once; a transaction a consumer runs through the event store directly does not, and its events reach the drainer at its next pass. A failure of the cycle -- a throwing retry-policy resolver, a pass that fails -- must not surface as a failure of the append that woke it, which had already committed. The event store holds the trigger of its one started, not yet closed cycle in a slot the cycle sets when it starts and clears when it closes, so no application code wires the two and a closed cycle is never woken.

**Why reruns, a cadence and a heartbeat record (assertion E)?** A trigger that arrives while a pass runs asks for work the running pass may already have passed over; dropping it would leave the change to the next trigger, which may never come. The cycle therefore runs one more pass, and a call that arrives meanwhile returns only once that pass has run; the check for a trigger that arrived and the end of the passes are one step, so a trigger that arrives as the last pass finishes either joins it or starts new passes. Other processes' appends and halt requests do not trigger this process's cycle, so the cycle also runs a pass at least once per cadence while it holds the lock; the cadence is a timer the cycle owns, re-armed whatever the pass did, and the lock is checked on a second timer so that a pass blocked in a send does not delay the detection of a lost lock. Each pass begins with a transaction that verifies the lock and writes a heartbeat record, so that any process can read when the drainer last passed. When that transaction does not commit (the read of the persisted schedules failed), the heartbeat record keeps the previous pass's value, and the pass still fills and sends the destinations its registry holds, each of whose transactions checks the lock and the persisted schedule itself.

**Why gate the test seams on assertions (assertion F)?** The seams let the library's tests observe the library's log lines and make a destination-registry operation, a fill, a drain outcome or the drainer's wedge fail at a named point inside its transaction, or make the drainer's wedge report failure after its transaction committed; they let the tests observe each inbound poll of the delivery cycle, make a drain-lock acquisition fail before or after the backend obtained its exclusion primitive (on Postgres also with a serialization failure or a statement that outlasts the query timeout inside the epoch raise, a failed verification through the pool, or a drain key the lock session holds outside the library), make a drain-lock heartbeat fail, hold an epoch raise, a queue-changing transaction, a lock grant or a committed transaction's publication at a named point while the test interleaves another party, and replace the timers of the delivery cycle's cadence and heartbeat and of a drain-lock request's retry; they also let the tests observe each run of `EventStore.open`'s boot transaction and make the boot fail after its library-version event, hold the incompatible-generation guard's boot lock at a named point, replace the timer that drives the Postgres lock session's probe, and make a generation registration, a probe, the ending of a lost lock session, the close of a lost lock session, a provisioning or the browser's lock manager fail, or the lock session's check fail as a transaction-mode pooler would. One seam is an environment signal: it narrows the page visibility the browser's drain lock follows, because a test cannot set it and two tab models in one page share one document; the page counts as visible only when both the seam and the page itself say so, so the seam can make a visible page count as hidden, never a hidden one as visible, and can only make a holder hand the lock over or a request wait, never grant a lock. Two seams are input substitutions: one replaces the package and data-format versions the boot decides with and records, and one replaces the Postgres migration list (and so the schema version and its minimum) of the backends and provisionings started under it, so that one test process can play two builds of the library against one database; with either installed, the checks decide and record as a build of those versions would. The library reads the installed seams only inside an assertion, so a release build, a program run without assertions, or a compiled executable never reads them: whatever a caller installs is ignored, and the seams are not an input that participates in any decision the library makes in production. They therefore add no entry to the library's trust boundaries. A seam may observe, delay, make an operation fail at a named point, replace a timer, narrow an environment signal, or substitute the build's declared versions or schema declaration; it cannot make an operation succeed that would otherwise fail except as the build it declares would, an observing seam that throws does not change what the library does next, and a seam never receives a database handle or a transaction. The residual is stated as it is: with assertions enabled (a test run, or a Flutter debug build) code that imports the internal seam file from the library's `src/` directory can install seams, the substituted build and schema declarations included, which then decide the boot or a provisioning and are recorded in the log or the database; that path is not one of the library's operations, so it lies outside the precondition of EVS-PRD-destinations/L, and the analyzer reports it as a use of an internal member.
