# EVS-DEV-version-compatibility: Entry-type and data-format versions

**Level**: DEV | **Status**: Active | **Implements**: -
**Refines**: EVS-PRD-event-log

## Purpose

How the library versions each entry type and its own data format, and what it lets builds of different versions do on one database and across ingest. An entry-type version and the library's data-format version are each a major and a minor number, and builds whose majors agree are compatible. The library enforces the rules it can check -- the shape of every registered promoter step, the majors at open and at ingest, and, through an incompatible-generation guard, that builds of different majors never run side by side on one database -- and states the rest as a precondition the consumer keeps.

## Assertions

A. The library SHALL identify each entry-type version by a major and a minor number, and SHALL treat two versions of an entry type as compatible exactly when their majors are equal.

B. The library SHALL refuse to register a promoter step within one major unless it leads to the next minor and every transform in it is a `DefaultField`, and SHALL refuse a step across majors unless it leads to minor 0 of the next major; a minor step with no registered promoter SHALL leave the payload unchanged.

C. The library SHALL declare a data-format version, a major and a minor number distinct from its package version, SHALL stamp it on every event it appends, and SHALL treat builds with the same data-format major as compatible.

D. On every ingest entry point the library SHALL refuse, before any write, an event whose data-format major differs from its own, whose entry-type major is above the registered major, or whose entry-type version is below the registered version with no registered promoter path from it for a view the event folds into; SHALL accept an event of the registered entry-type major at any minor, folding it unchanged when its minor is not below the registered minor; and SHALL accept an event of an entry type it does not register at any version.

E. When the library folds an event into a view under a registered entry-type version whose major equals, and whose minor is below, the view's stored target version for that entry type, it SHALL lower the stored target to the registered version in the same transaction.

F. Before any write, `EventStore.open` SHALL refuse to open a database while another live instance of the library on that database holds a data generation that conflicts with its own; otherwise it SHALL register its generation until the event store is closed, and SHALL release the registration when the open fails after registering. Two generations conflict when their data-format majors differ or an entry type both register has different majors.

G. The library SHALL serialize, per database, the generation inspection, registration and boot transaction of instances opening it, and the provisioning of that database, so that of two conflicting instances opening at the same time at most one opens.

H. The generation guard SHALL cover every process and session on a Postgres database, through a lock session verified to be one server session reaching that database, and every tab of an origin on a web database, where a page without a lock manager SHALL be refused; on Sembast outside the browser the library relies on the database file being opened by one isolate of one process.

I. The library SHALL record, per database, the highest generation that has booted, and SHALL treat that record as admitting a build unless it records another data-format major or, for an entry type the build registers, a higher major. `EventStore.open` SHALL refuse, before any write, a build the record does not admit; an instance whose registration is lost SHALL check the live registrations, the record and, on Postgres, the stored schema version pair before it registers again; and an instance SHALL commit no transaction while the record does not admit its build or, on Postgres, the stored schema pair is one it does not support, which on Postgres every transaction SHALL verify before its first write.

J. The library SHALL include an event's entry-type version and data-format version in the content from which the event's hash is derived.

K. The boot transaction of `EventStore.open` SHALL append a registry audit event recording, for every registered entry type, its major and minor version and the kind and eligibility it declares for each event type, whenever the registered set, any registered major or minor, or any registered entry type's declarations differ from the latest registry audit it appended.

L. Whenever the library folds a newly stored event into the views it registers, it SHALL also record, in the same transaction, a catch-up gap covering the event on the view of every stored view target of the event's entry type whose view it neither folds the event into nor registers for that entry type.

M. When the library folds an event into a view under a registered entry-type version whose major equals, and whose minor is below, the view's stored target version for that entry type or the round version of that pair's promotion gap, it SHALL, in the same transaction, record a promotion gap for the pair covering the event, with the higher of that stored target and that round version as its round version and its registered version as its prior version.

N. The library SHALL declare data-format version 3.0.

O. `EventStore.open` SHALL refuse, before any write and with `DatabaseResetRequiredError`, a database holding an event that a build of data-format major 2 or below appended.

P. Every ingest entry point SHALL refuse, before any write and before decoding the batch, a batch in an envelope format that data-format major 2 or below used, naming the envelope format and that data-format major.

Q. Every ingest entry point SHALL refuse an event in a supported envelope whose data-format major is 2 or below before any refusal that concerns the rest of that event's record, naming the event's data-format major.

R. <RETIRED> A changed declaration of kind or eligibility is no entry-type major step: every event records its own kind and eligibility under its hash, and every reader reads the recorded values.

## Rationale

**Why do majors decide compatibility (assertions A to D)?** Builds registering different minors of one major read and write each other's events when a minor bump only adds optional fields: an older build ignores a field it does not know, and a newer build supplies the default for a field an older event lacks. The same holds for the record around the payload: a build keeps, as they arrived, the initiator's keys, the version maps' keys and the record's top-level keys it does not read (EVS-DEV-event-record/B), and a version is read from its major and minor whatever else its map carries, so a record written by a later release of the same data-format major verifies, stores and relays unchanged through an earlier one, and a library-version event, a view target or a boot record that such a release wrote opens under it. That a minor bump only adds optional fields -- that producers do not rename, drop or re-type a field within a major -- is a precondition the consumer keeps; the library does not see producer code, and a minor bump with no promoter is legal. What the library enforces is what it can check. Registration refuses a same-major promoter step whose transforms are not all `DefaultField` and a step across majors that does not lead to minor 0 of the next major, so no registered promoter renames or drops a field within a major. Open and ingest compare majors. Ingest applies the rule to events from peers: a same-major event is accepted at any minor; one of a higher major is refused before anything is written, and so is one of a different data-format major, which this build has no reader for; and one below the registered version is refused by name when a view it folds into has no promoter path from its version, because the fold could not promote it. An event of an entry type the receiver does not register is accepted at any version and stored as it is, as a relay stores what it forwards; it folds under its own version into any view whose interest names it. The version rules decide which versions ingest accepts; an accepted event still passes the other ingest checks, among them the reserved-event checks (`EVS-DEV-destination-drain/L`), whose declared shapes are fixed within a data-format major, so they refuse no event that a library of the receiver's data-format major appended, at any minor.

**Why is a change of declarations no major step?** An event type's kind and eligibility decide the causal parents the library stamps, and each event records its own under its hash. The stamping rule, the conflict records and the chain verification read those recorded values, never a build's declarations (`EVS-DEV-causal-parents`), so a build that declares an event type otherwise, beside or after another build of the same major, records its own events truthfully and misreads no other build's. Nothing in the log becomes untrue, so the library does not tie a change of declarations to the entry-type major.

**Why does a fold lower the stored target, and record a promotion gap (assertions E and M)?** In a canary overlap the older-minor build is the one already serving: it never reopens, and it keeps folding after the newer build's boot raised the stored target and while the newer build's promotion runs. The rows it folds lack the newer minor's fields. Lowering the stored target to the version it folded under records that the view is no longer wholly at the newer minor, so a build of the newer minor that opens later finds a stored target below its registered version and re-promotes the view. The promotion gap it records names the aggregate it folded and keeps the newer minor as its round version, so a build of the newer minor that is running re-derives that row by view convergence without waiting for an open, and a promotion in progress does not complete over a row the older build folded after convergence re-derived it (EVS-DEV-view-convergence). M fires also when an earlier fold already lowered the target to the folding build's version, since the gap's round version still records the newer minor. The older build's own convergence re-derivations are folds here (EVS-DEV-view-convergence/K), so an older build that catches a view up with missing events records the rows it re-derived in the same way. Re-derivation folds the row's events from the log (EVS-DEV-snapshot-promotion-on-open/B), so the rows equal a replay under the newer build's versions. The fold lowers a target, and records a gap, only for the views the folding build registers; a view, or an entry type in a view's interest, that only the newer build registers is covered by assertion L.

**Why is the data-format version distinct from the package version (assertion C)?** A release that changes no stored or sent shape is compatible with its predecessor whatever its package version. The data-format version names exactly the stored and sent shapes, so the compatibility decision rests on what a build can read, not on its release number. A data-format major bump, like an entry-type major bump, is a stop-then-start deployment: every instance of the old major stops before one of the new major starts.

**Why a live generation guard (assertions F to H)?** A major bump -- a data-format major, or an entry type's rename or drop -- is deployed stop-then-start: every instance of the old revision stops before the first instance of the new one opens the database. The guard enforces that order instead of trusting it. Every open registers its build's generation before its boot writes anything, and holds the registration until its event store closes; an open that meets a live instance of a conflicting generation is refused with nothing written, so a canary of a new major cannot open beside the serving revision, and an old revision cannot come back while the new one runs. A generation is registered as components -- the data-format major, and each registered entry type's major -- rather than as one value, because adding an entry type is a compatible change: a canary that registers an entry type the serving revision does not know shares every component the two have in common, and conflicts on none. Minors never conflict. Registration, inspection and the boot transaction run under one exclusive boot lock per database, which provisioning also takes, so of two conflicting opens at the same moment one inspects, registers and commits before the other inspects, and the durable record, the log and the live locks are decided together. Two opens on one Postgres backend share its lock session, where an advisory lock is re-entrant, so the backend also orders its own opens one after the other. A lock session lost while a boot runs is replaced with that boot's registration, and its boot lock, taken again on the new session. On Postgres the locks are session-level advisory locks held on a dedicated lock session, which the server releases when the instance exits or its session ends; the lock session must be one real server session (EVS-DEV-postgres-backend/J). On the web they are Web Locks, which the browser releases when a page closes; a page without a lock manager (Web Locks exist only in a secure context) cannot tell whether a tab of an incompatible build is open, so it is refused rather than admitted. On the web every `SembastBackend` registers, an in-memory one included: sembast's public API does not tell an IndexedDB database from an in-memory one, and guarding by name can only refuse an in-memory database, never admit one a shared database would refuse. A Sembast database outside the browser is trusted to be opened by one isolate of one process -- a deployment precondition the library cannot check, since two processes, or two isolates of one process, that open one file see no lock of each other -- so it has no live guard; the durable record still refuses an older build there. Keys are derived from a hash of the database, the schema and the component; a collision could only make a live component look like another one and refuse a boot, the safe direction, and its probability is negligible.

**Why a durable record, and one comparison (assertion I)?** The live guard sees only instances that are running. The durable record covers the rest: every boot that commits merges its generation into it -- the data-format major, and for each entry type the highest major any boot registered -- so a build of an older major that opens after the new one stopped is refused, including for an entry type no view names (the stored view targets record only the entry types a view names). The record admits a build unless it holds another data-format major or, for an entry type the build registers, a higher major; a recorded major below the build's is the stop-then-start bump itself, which that build's boot raises. The boot and the transaction fence use this one comparison, so the same scenario refuses with the same exception on every backend. On Postgres a running instance can lose its registration: its lock session can end while the process lives. It then checks, before it registers again, the live registrations, the record and the stored schema pair, and while it is not registered, every transaction reads the record and the schema pair before its first write and refuses when they do not admit it. The read is a plain read under serializable isolation: a transaction that read the older record and commits after a conflicting boot or provisioning is ordered before it by the database, and any overlap between what it wrote and what the other read or wrote makes one of them fail and retry; a transaction that starts after the other committed reads the new values and refuses. What remains is a transaction of the stale instance that the database orders before the conflicting boot, which is correct under serializable ordering: nothing it commits is ordered after that boot. An instance whose registration cannot be taken again is fenced -- it commits nothing, holds no generation lock, so it never stands in the way of the build that fenced it, and must be stopped. The record is a gate kept in storage beside the log, not a fact derived from it: a data-format change is also recorded in the log (the library-version events), but a raised entry-type major is recorded only in the record, so the refusal of an older entry-type major rests on that record, and on the stored view targets, rather than on a replay of the log. The guard covers the data format and the entry-type majors; a change to a projection specification is not versioned, and two builds with different specifications for one view do not conflict.

**Why do the versions enter the event hash (assertion J)?** The versions decide whether ingest accepts an event and how it is promoted, so a forwarder that rewrote them would change what the receiver folds. Covering them by the hash makes such a rewrite break the event's hash and, at the next hop, the chain.

**Why do views catch up with the log (assertion L)?** Builds that share a database need not register the same views: a canary may add a view, or an entry type to a view's interest, that the serving build does not register, and a rollback may put such a build back in service. The build that does not register the view does not fold what it appends or ingests into it, and a view registered on a database that already holds events starts with none of them. A lowered version cannot record this -- a target at minor 0 cannot be lowered, and the difference is not one of version -- so the build that did not fold the event records a catch-up gap naming it, in the transaction that stores the event, and the boot of a build that seeds a view's target over events already in the log records a catch-up gap covering the whole log (EVS-DEV-view-convergence). Any build that registers the view re-derives what a catch-up gap covers after its open, in short transactions of its own, through the fold step every fold path shares (aggregate views by the aggregates the gaps name or the log holds, table views by refolding in log order), so the view equals a replay; until it has, the view is reported as converging for that build and its unsettled rows are withheld (EVS-DEV-converging-view-reads). While the build that lacks the view keeps storing events of the view's entry types, each records a gap, so the view converges again after each such store until convergence catches up, and stays current once that build stops. A build that registers the view and names the entry type records nothing, whether or not its interest matches a given event: that build's interest is the view's definition. The per-entry-type gaps cover the pairs a stored target names, which are the entry types a view's interest names explicitly; a view whose interest names no entry types -- it selects by aggregate type, or matches every entry type -- has a whole-view row instead, for which a build that does not register the view records every event it stores (EVS-DEV-view-convergence/D). Two builds whose interests for one view differ only outside the named entry types -- in aggregate types, or in whether system events are included -- both register the view, so neither records a gap, and the events only the wider interest matches stay out of the view the narrower build folds; for those views `rebuildView`, run once no build holding the narrower interest still serves the database, brings the view level with the log. A catch-up appends no audit event, where snapshot promotion appends one per completed promotion: promotion records that the version a view folds an entry type under changed, while catch-up applies an unchanged definition to events the log already holds. The view is derived state; the log and the library-version events that record which builds opened the database are what a reader replays, and the gaps are storage state kept beside the views (EVS-PRD-destinations/L).

**Why record every major and minor, and the declarations, in the registry audit (assertion K)?** The registry audit is how the log records which entry-type versions a database was opened with. Recording the minor as well as the major means a minor raise is recorded as a major raise is, and an unchanged registry appends nothing. The kind and eligibility an entry type declares for each event type decide the causal parents the library stamps, so recording them lets the log show which declarations were in force when each event was appended. The library compares them with no other build's: each event carries its own.

**Why data format 3.0 (assertion N)?** Data format 3.0 is one major step that carries every stored and sent shape the library adds with it:

- the database identity and the library version on every provenance entry, and the storage-chain link on the last entry of every stored event (EVS-DEV-event-record/D and E, EVS-DEV-chain-verification/C);
- the causal record on every event, covered by the event hash, and the kind and eligibility declarations the registry audit records (EVS-DEV-event-record/J and K, EVS-DEV-causal-parents);
- the delivery channel's fields in the batch envelope, the withheld-parent record and the break, and the receiver's delivery stamp in its provenance entry;
- the receiver's record and identity in the acknowledgement and the refusal, the pull and refusal bodies, and the `rejected` refusal with its named reason;
- the reserved events for a resumed channel, a succession, a security finding and the receiver's delivery audits, the new wedge causes, and the reconciliation;
- the reserved `$` row namespace and the view convergence records, and the promotion audit without a row count.

A field the library requires, and refuses a record without, cannot be added in a minor: every event an earlier minor of the major appended lacks it, so the later minor would refuse its own major's events. The library's own ingest keeps earlier provenance entries as the record carries them, so a field added only as optional would survive a receiver of an older minor storing the record and serving it back in a recovery or restore pull. Code outside the library that decodes an entry into the provenance package's value type of an earlier release and encodes it again can drop such a field (EVS-PRD-provenance/E). The version numbers are a Layer 2 convention (the library's major.minor rule); the refusals they decide are checked.

**What an older database and an older peer meet (assertions O to Q).** A build of data format 3 opens only a database of its own major. A database a 2.x build wrote is refused before any write: its latest event lacks `library_version`, which the first read of the boot refuses as malformed, so the open refuses it as a database that must be reset (assertion O; EVS-DEV-event-store-open/F, which takes precedence over D). The two refusals agree that no 3.x build opens the database, and no release reads an older data-format major (`spec/roadmap/versions.md`). A 3.x build cannot open beside a live 2.x instance, because its generation conflicts (assertion F). A 2.x peer sends batches in the envelope format of its data format; ingest refuses such a batch before decoding it, naming the envelope format and the data-format major it implies (assertion P), and the peer's drainer records a permanent failure. A 2.x record carried in a 3.x envelope is refused by its data-format major before any check of the record's shape (assertion Q), so the reason names the version and not a missing field. Deploying data format 3.0 is therefore stop-then-start across every database and every peer that exchange events, and it starts from empty databases: a device holding events a 2.x build appended, sent or not, is reset (EVS-DEV-storage-capability/L deletes a Sembast database by its description).
