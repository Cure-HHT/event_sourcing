# EVS-PRD-destinations: Destinations

**Level**: PRD | **Status**: Active | **Implements**: -
**Refines**: EVS-PRD-library-charter

## Purpose

A destination is a configurable outbound channel through which a deployment delivers selected events to another system. The other system may be another event-sourcing deployment (e.g., a sponsor's data store, an EDC), a passive sink (e.g., a webhook), or a notification service (e.g., a push-notification gateway). The library handles event selection, ordering, durability, and hand-off; the actual transit is performed by a configurable per-destination delivery mechanism.

The library treats destinations as a write-side concern only. Inbound flow from another event-sourcing deployment is specified separately in EVS-PRD-ingest.

## Assertions

A. The library SHALL support configuring destinations on a deployment.

B. Each destination SHALL be configured with a filter that selects which events the destination receives.

C. The library SHALL queue for delivery on each destination, in FIFO order, the events the deployment authored that match the destination's filter and schedule, together with the resume, succession and security-finding events the library enqueues for that destination, and no event the deployment did not author, whatever that event's age.

D. A destination's queue SHALL be durable: queued events survive a deployment restart and are delivered when the deployment resumes.

E. The library SHALL accept an application-supplied delivery implementation for each destination, to which the library hands queued events for transit (HTTP webhook, push notification, custom transport, and so on are example implementations the application may provide).

F. Destinations SHALL be addable and removable dynamically over the deployment's operating lifetime.

G. While delivery on one destination is failing, the library SHALL continue delivering queued events on every other destination.

H. If an application-supplied delivery implementation raises an error while transiting an event, then the library SHALL treat that error as a failed delivery attempt.

I. The library SHALL leave an event whose delivery attempt failed at the head of its destination's queue.

J. The library SHALL record each delivery attempt made for a queued event, except an attempt whose outcome transaction did not commit: its drainer was closed or lost the drain lock, its process stopped, or the storage failed to commit the outcome.

K. The library SHALL mark as internal every public member, other than opening and closing an event store, provisioning a Postgres database, the event store's append, transaction, ingest and reconciliation operations, the destination registry's operations, the delivery cycle's operations, the receiver endpoint's operations, the restore operation, the view rebuild, the security-context redaction, compaction, purge and retention operations, the idempotency store's record, lookup and sweep operations, the Sembast database delete operation, and its storage backend's transaction and close operations, that changes a destination's queue, a view the library materializes, the library's persisted delivery state, the security context stored beside an event, the event sequence or the storage schema version, appends an event without the event store's checks, publishes to live subscribers something the library did not append, or exposes a raw handle to the database or to a transaction's underlying engine transaction.

L. The library SHALL state, as a precondition of its storage trust boundary, that its delivery guarantees, its views and its security-context records hold only while no code other than the library writes the storage of a database the library opened -- through a connection made with the credentials of the library's Postgres roles, or by a role that administers the database (the owner of its tables, a superuser, a role holding `CREATEROLE` or the admin option over a library role), through a handle opened on the location of its Sembast database or on the file itself, or, on the web, by script on the page -- and while the library runs in a build with assertions disabled; and, for a database opened over a storage backend the application supplied, only while its persisted state (destination queues, the views it materializes, the records it keeps beside them, such as fill positions, schedules, replay requests, wedge records, halt requests, send fences, refill guards, the sender channel records of its delivery channels, the chain index, the per-aggregate causal working copies, the registry check record, the database identity, the generation records, the declared library roles, the view convergence records (convergence gaps), the fencing epoch and the declared configuration, and the security context it stores beside each event) changes only through the library's operations and reserved system events are appended only by the library's own operations.

M. The library SHALL refuse an operator recovery of a destination's queue unless the queue's head item is wedged.

N. An operator recovery SHALL rewind the destination's fill position below the lowest event carried by every queue item the recovery removes, so that a later fill re-evaluates each of those events against the destination's filter and schedule.

O. The library SHALL refuse to delete a destination while its queue head is pending; a deletion SHALL retain every queue item that was delivered, wedged or recovered; and a destination registered again under the same identifier SHALL start a new registration whose fill delivers, under its own schedule and filter, the events its window admits.

P. When the library wedges a queued item, the library SHALL append a wedge event in the same transaction that marks the item wedged.

Q. The wedge event SHALL record its cause: the delivery implementation reported a permanent failure, the retry budget was exhausted, an operator requested a halt, the delivery implementation reported an acceptance that carries no receiver record, or a delivery channel's check-in reached no receiver endpoint of this library.

R. The wedge event SHALL contain no text from the outcome the delivery implementation reported for an attempt (error message, stack trace or response body).

S. The library's default destination-wedges view SHALL TREAT a destination of a database as wedged from the wedge event that names it until a recovery event or a deletion event that names it, deriving its rows solely from those events, other than those whose originating database is the holding database and that it does not hold as authored.

T. The library SHALL append a recovery event when an operator recovers a wedged queue, and a deletion event, naming any wedged item it retires, when a destination is deleted.

U. The library SHALL record an operator's halt request, and its cancellation, as events in the log, and SHALL honour an open halt request by wedging the destination's queue head; at most one delivery attempt on that destination, one whose pre-send check the database orders before the request, SHALL complete after the request, other than one started by a drainer that has since lost the drain lock.

V. Within the scope its storage backend supports, the library SHALL let at most one drainer commit queue changes for a database at a time. A delivery cycle started while another holds the database SHALL stand by and take over when it is released, and a second delivery cycle for one database handle within one isolate SHALL be refused.

## Rationale

**Why a configurable filter per destination?** Different destinations care about different slices of the event log. A sponsor EDC wants only the events for participants in that sponsor's trial; a push-notification gateway wants only notification-emitting events. Pushing the entire log to every destination wastes everyone's resources and leaks data across boundaries. Filtering at the destination configuration concentrates that work in the library.

**Why FIFO queueing, and only authored events (assertion C)?** Downstream systems typically consume events incrementally and expect to see them in the order they were produced. Out-of-order delivery makes downstream materialization incorrect, even when the events themselves are individually well-formed. A FIFO queue per destination decouples the deployment's event-production rate from the destination's delivery rate while preserving order. A destination carries what its deployment authored: events appended locally, whose originator entry names the deployment's database. An event the deployment ingested, or restored from a predecessor, belongs to the database that authored it; enqueuing it would send a receiver a third party's events as if this deployment were their sender, and a delivery channel's recovery relies on every delivery holding only its sender's events (EVS-PRD-delivery-channel). An event the deployment recovered as its own from one channel's receiver is its own authored event: it is delivered on the deployment's other channels, never back on the channel it came from. A deployment therefore does not forward what it ingested: each deployment delivers its own events to each receiver that needs them. The rule looks at provenance, not at a date window, so an old event ingested today is excluded as surely as a new one. The resume and succession events are the library's records of the channel and the sender themselves, and it enqueues them whatever the filter, because the receivers must receive them.

**Why durable queues?** A non-durable queue loses events on restart, which means the audit trail held by upstream and downstream diverge whenever a process restarts. Durability across restart is the property that lets the destination's recipient trust that "if I haven't seen event X yet, it has not been delivered" — a precondition for at-least-once delivery semantics.

**Why pluggable delivery mechanisms?** Real deployments transit events over a wide range of transports — HTTPS to a clinical EDC, push notifications to mobile devices, a relay's own HTTP endpoint, a sponsor's custom protocol. Picking one transport in the library would force every consumer to either use that transport or shim around it. Treating the transport as a per-destination plug-in keeps the library transport-agnostic.

**Why isolate failure between destinations?** Destinations fail independently and for unrelated reasons — a sponsor's endpoint is down for maintenance while a push gateway is healthy. Because each destination's queue preserves order, an undeliverable event at the head necessarily halts that queue; if that halt also stopped the other destinations, one unreachable recipient would silently stop delivery to every recipient. Isolation is what makes a per-destination queue a containment boundary rather than a shared point of failure.

**Why an exception to recording every attempt (assertion J)?** The outcome of a send is recorded in one transaction after the send returns. When that transaction does not commit -- the drainer was closed with a timeout, or lost the drain lock to another drainer, or its process stopped, or the storage failed to commit -- the queue item stays pending with no record of the attempt, and the next pass sends it again. The receiver may then hold a delivery the queue has no record of, and receive it twice: delivery is at-least-once. The rule covers every attempt whose outcome commits.

**Why treat a raised error as a failed attempt rather than a lost event?** The delivery implementation is application-supplied and therefore outside the library's control: it may throw on a DNS failure, a timeout, or its own bug. Three outcomes are possible when it does — drop the event, propagate the error to the caller of the delivery pass, or record the failure and retry. Only the third preserves the at-least-once semantics the durable queue exists to provide, so it is the one the library commits to. Recording the attempt (rather than silently retrying) is what makes a wedged head diagnosable: an operator can see how many times an event has been tried and with what outcome, which a bare retry loop does not expose.

**Why mark the mutating surface internal (assertion K)?** A destination's delivery guarantees rest on its queue, its fill position and its schedule changing only in the order the library's own operations change them. A direct queue write can mark a row terminal behind the drain's back, a direct view write produces a row that no event in the log accounts for, and a direct write to an event's security context bypasses the redaction and purge events that record such a change. Marking every such member internal -- on the exported types and in the library's `src/` files alike -- makes a consumer's call to it an analyzer error while leaving the library's own operations as the consumer's entry points: the delivery cycle, the destination registry, the event store, the view rebuild, and the backend's transaction and close. The view rebuild qualifies because it folds the log at each entry type's registered version and refuses any other target, so it writes only rows that the log and the entry-type registry determine; it does not notify live subscribers. An event-store append inside a consumer's transaction is accepted only in the event store's own transaction, through the collector of the run that commits it, so live subscribers receive exactly the events that committed. The rule is an analyzer guard over the library's own surface. For the storage the library opens itself, the run-time barrier (EVS-PRD-storage-barrier) goes further: no object the application holds carries these members, so a call that ignores the analyzer, or is made dynamically, finds none. For a storage backend the application constructs and supplies, the analyzer guard is the whole protection: it reaches a backend in another package only where that package marks its own overrides of the internal members internal, and a backend declared in the application's own package is covered by assertion L alone.

**Why state a precondition on the storage trust boundary (assertion L)?** No object the library hands the application writes its persisted state or appends a reserved system event outside the library's public operations (EVS-PRD-storage-barrier). On Postgres the library also refuses to open a database on which a role outside the owner and its declared roles may write its tables. What neither can stop is a writer that holds the storage itself, which takes these forms:

- A connection made with the credentials the deployment gives the library's Postgres roles, from any process, the application's own included, since the application puts those credentials in the storage description.
- A role that administers the database: the owner of the tables, a superuser, a role holding `CREATEROLE`, or a role holding the admin option over a library role. Each can give itself a library role's writes.
- A Sembast handle opened on the location the library opened (sembast hands the handle already open on a location to a second open of it in the same isolate), or the file edited directly.
- On the web, script on the page, which can walk a compiled Dart object's fields and open the library's IndexedDB database by name.
- A build with assertions enabled, whose test seams can substitute what the library declares and whose test-only constructor takes a backend.
- A storage backend the application constructed and supplied, which the application holds by construction.

The library cannot detect such a write, so its delivery guarantees and its views are stated as holding only while no such writer changes its storage. The records kept beside the queues are these:

- the fill positions and the schedules;
- the replay requests a registry operation leaves for the next fill;
- the wedge record the drainer writes beside each wedge event;
- the halt request an operator opens and the transaction that closes it removes;
- the send fence the drainer writes before each send;
- the refill guard an accepted recovery of a reconfigure halt leaves;
- the sender channel record of each delivery channel (the receiver record, the receiver's identity and the check-in epoch);
- the chain index (which also locates each delivery channel's latest accepted-delivery audit on a receiver), and the per-aggregate causal working copies;
- the registry check record;
- the database identity the first open mints and records in the log;
- the generation records: the highest data generation any committed boot registered, and, on Postgres, the records that map the generation guard's lock keys back to their components;
- on Postgres, the declared library roles;
- the view convergence records: the convergence gaps a boot, a store by a build that lacks a view, a fold under an older minor, a skip event, a reconciliation, a security finding or a rebuild records, with the aggregates they name and hold as re-derived and their positions;
- the fencing epoch every acquisition of the drain lock raises;
- the declared configuration, with the unserved destinations and the heartbeat, that the drainer records at the start of each pass.

A write that bypasses the library's operations has these effects on those records:

- A replay request written or removed directly would make the next fill enqueue a replay no operation requested, or skip one an operation recorded.
- A wedge record written or removed directly would name a wedge the log does not record, or hide one it does.
- A halt request written directly makes the drainer halt at a request the log does not hold, but only when it cites a halt request event of the destination (the drainer checks the cited event, not whether a later event closed it). One removed directly leaves unhonoured a request the log records as open.
- A send fence removed or written directly changes nothing the drainer decides, since the fence transaction rewrites it before each send.
- A sender channel record written directly changes the number and link of the next delivery, so the receiver refuses it and the channel resumes from the receiver's record, or, when the record written is the receiver's own, lets the drainer skip a check-in; a check-in epoch written directly lets a drainer send before it has learned where the channel stands.
- A chain index or a per-aggregate causal working copy written directly makes the next append name the wrong predecessor or parents, lets ingest accept a fork or refuse a sound event, makes a receiver read a channel's record from the wrong audit, or allows an edit of an aggregate whose conflict is still open, until the chain verification reports the copy against the log.
- A database identity written or removed directly makes every later open refuse the database, since the identity recorded in the log no longer matches.
- A generation record lowered or removed directly lets a build the database had refused open it. One raised directly refuses a build it had admitted and fences the instances running it.
- A declared role added directly admits a writer the open would refuse.
- A convergence gap removed directly makes a view read as current, and its rows as settled, while it lacks events or a promotion the gap recorded. One written directly makes a view converge again, withholding the rows it covers until convergence re-derives them. An aggregate marked re-derived, or a position moved, directly can make convergence skip rows it had still to re-derive.
- A fencing epoch written directly makes the current drainer's next transaction refuse, since it no longer holds the epoch it acquired. If the value written is a replaced drainer's own, that drainer can commit again.
- A refill guard removed directly lets a drainer that still declares the configuration a reconfigure halt stopped refill under it. One written directly holds a destination unserved.
- A declared configuration written directly decides whether a recovery of a reconfigure halt is accepted.

Reserved system events are records of the library's own operations: the destination audits, the wedge event, the channel resume and succession events, the security-context and retention audits, the registry audit, and the library-version and ingest audits. The event store's public append operations refuse their entry types, ingest refuses one in a shape the library does not append, and only the library's own operations append them: the public ones among them are a closed list, each appending only the reserved events its own operation defines (`EVS-PRD-storage-barrier/C`), and every other operation that appends one is private to the library. A reserved event written into the log by a writer that holds the storage would state an operation that did not happen, and a view the library folds from it, such as the default destination-wedges view, would show a wedge no drainer recorded. The precondition covers such an event because it covers every write such a writer makes. It names reserved system events explicitly for a database over an application-supplied backend, whose holder can call the internal append operations. Stating the precondition beside the storage trust boundary names the gap, as the charter's trust-boundary enumeration requires. The idempotency cache an application supplies to action dispatch is not part of this state: the cache is a pluggable interface the application may implement itself, so the library's guarantees do not rest on its records.

**Why does recovery require a wedged head (assertion M)?** A pending head may be in delivery: the process that drains sends outside any transaction, and an operator recovery running elsewhere cannot see the send. Retiring a pending head would race the delivery's outcome, and would record a recovery where no delivery halted. A wedged head is never in delivery, because only the drainer wedges a head, after its own send returned. An operator who needs to rebuild a healthy queue, for example after changing the destination's transform or filter, first requests a halt, which the drainer honours by wedging the head (assertion U), and then recovers. A recovery attempted while that request is open and not yet honoured is refused with a message that says to wait for the drainer, so the two steps cannot be taken in the wrong order.

**Why rewind below every removed item (assertion N)?** Recovery is "discard and rebuild from the log", not "skip the bad item": the removed items' events are evaluated again by the next fill, under the destination's current filter and schedule, so a changed transform or filter takes effect on them. An item removed from behind the head can carry events lower than the head's (a replay of an earlier window enqueues old events at the tail), so the rewind goes below the lowest event of every removed item; rewinding only below the head would lose those events. Events that were already delivered and lie above the rewind point are delivered again: delivery is at-least-once.

**Why refuse to delete a pending head, and keep the delivery record (assertion O)?** Deleting a pending head could discard the record of a delivery the receiver accepted while the deletion ran. Items that were delivered, wedged or recovered are the destination's delivery record; they outlive the destination so that an auditor can still see what was sent. A destination registered again under the same identifier starts a new registration and delivers from its own schedule; its refill may send again events that the old registration delivered, which is at-least-once delivery.

**Why append a wedge event with the wedge (assertion P)?** A wedged item halts delivery on its destination until an operator recovers it, and the operator, an auditor and any process that reads the log need to know that the halt happened, where and why. Appending the event in the transaction that marks the item wedged makes each wedge event the drainer appends agree with the queue at its commit: both commit or neither does, so when the event commits the item it names is wedged, and no item the drainer wedges lacks its event. The agreement is scoped to wedge events the drainer appends for its own database: the event store's public append operations refuse this entry type, and under the precondition of assertion L (no object the library hands the application exposes the append operation the drainer uses, EVS-PRD-storage-barrier) only the drainer appends it within the database; a wedge event a peer forwarded carries only what the peer asserts. This is a Layer 1 fact, scoped to events the library appended for its own database: the log records that the drainer marked the named item wedged, atomically, with the drainer's attribution, and with the outcome category and numeric status the delivery implementation reported. It says nothing about whether the receiver was right to refuse the item; that judgement belongs to the delivery implementation, which the library trusts.

**Why record the cause (assertion Q)?** The attempt count and the last outcome do not say why an item wedged: a budget exhausted by transient failures ends on a transient outcome, which reads as retryable, and a halt requested by an operator involves no failure at all. Recording the cause lets the log distinguish a receiver's refusal from a spent budget from an operator's decision, and lets an operator choose the recovery each calls for (fix the receiver, raise the budget or wait out the outage, or resume after the change the halt was for). The delivery-channel causes name deployment faults that no retry changes: a transport that reported an acceptance without the receiver's record, and a check-in whose pull reached no receiver endpoint of this library. No integrity anomaly wedges a channel: the library records it as a security finding and delivery continues (EVS-PRD-delivery-channel).

**Why no attempt text in the wedge event (assertion R)?** The event log is append-only and forwarded to other systems, so whatever the wedge event carries stays there for the life of the log. A receiver's error message can echo back the payload it refused, and a thrown exception's text and stack trace can carry payload fragments, host names or credentials. The wedge event therefore records only structured fields (the item, its events, the cause, the attempt count, the budget in effect, the outcome category and the numeric status), and the full diagnostic stays on the queue item's recorded attempts, which the library keeps beside the queue and does not forward.

**Why a default destination-wedges view, and why a convention (assertion S)?** Consumers need the wedged destinations as state they can read and subscribe to, not as a condition inferred by polling each queue head. The library folds that state from the log with its declarative Table interpretation: a wedge event inserts a row for its destination, a recovery or a deletion removes it, and no other event touches it. This is a Layer 2 convention, the library's default interpretation of which destinations are wedged now, and its `default` name says so; an application wanting another reading folds the same events itself. Rows for the database itself mirror its queues under the precondition of assertion L: a destination has a local row exactly while its queue head is wedged, because every path that wedges a head or ends a wedge appends its event in the same transaction, and no other code appends those events. A row is local when its `database_id` field is the database's own identity. A recovery brings back the database's own events of a history it abandoned, wedge and recovery events included; they stay in the log as facts of that history, and the view folds none of them, since they describe queues the database no longer has, so a local row still exists exactly while the head is wedged. Rows for another database rest on the database identity its forwarding peer asserts, which the receiver does not verify, and reflect the peer's queue only when the peer forwards all three event types and delivers a wedge before the recovery or deletion that ends it: a peer guarantees order only per aggregate per source, and a wedge and its recovery can carry different aggregates when different instances append them, so a remove that arrives first changes nothing and the later wedge row stays.

**Why an event for every end of a wedge (assertion T)?** The view removes a destination's row only on an event, so any path that ended a wedge without one would leave the destination shown as wedged forever. A recovery and a deletion are the two paths that retire a wedged head; each appends its event in the transaction that retires the head, and a deletion names the wedged item it retired so the log reads which wedge it ended. A deletion of a destination with no wedged head records no retired item and leaves the view unchanged.

**Why an operator halt the drainer honours (assertion U)?** A halt request and its cancellation are operator actions that change what the drainer does, so each is an event in the log, and the log alone says when delivery was asked to stop and by whom. An operator needs to stop delivery on a healthy destination, for example to rebuild its pending items under a changed transform or filter, and a halted destination must look exactly like any other wedged one so that the same recovery applies. Writing the wedged status directly would race a send in flight in the process that drains: the send runs outside any transaction, and its outcome would then find its item already wedged. The operator therefore records a request, and the drainer, the only writer of the wedged status, honours it by wedging the head itself before its next send; a send already in flight completes and its outcome is recorded, and the wedge event records the cause operator halt, so the log reads that an operator halted delivery, not that a delivery failed. The bound is at most one attempt after the request: immediately before each send the drainer runs a check in a transaction that writes, and that check refuses to send while a request is open. "Orders before" is the database's serialization order, which on a serializable server database can differ from the order in which the two transactions' commits completed by the wall clock; the bound still holds, because a check the database orders after the request sees it, and the check of the drainer's next iteration runs after the one attempt's outcome committed. A drainer that lost the drain lock while its send was on the wire (assertion V) is the one exception: its send can complete after the request, and its outcome commits nothing.

**Why at most one drainer per database (assertion V)?** The drain reads the queue head, sends it outside any transaction, and records the outcome; two drainers of one database would send the same head twice and race each other's outcomes, and every guarantee above that names "the drainer" would lose its subject. The library therefore excludes drainers rather than trusting the application to start only one. A delivery cycle takes the database's drain lock before it drains; one that cannot take it stands by and takes over when it is released, without a restart, so a deployment may start a cycle in every process and exactly one drains. The scope is what the storage backend can exclude on, and is stated per backend in EVS-DEV-destination-drain-lock/A: every process and session on a Postgres database stands by, and on Sembast outside the browser the scope is one isolate per open database handle, which is also all that Sembast's file storage supports (one open handle per file per isolate), so a second isolate that opens the same file is outside what the backend supports and outside what the library claims. In the browser every tab of an origin on a database stands by but the one that holds the lock, and the lock follows the visible tab: a tab whose page becomes hidden releases it once the outcomes of its sends in flight commit (waiting at most one cadence for a send that does not return), and does not request it while hidden, so the delay is about one cadence while any tab is visible, and nothing drains while no tab of the origin is visible. A page frozen before its release completes keeps the lock until it resumes or is discarded, and the visible tab stands by until then; this is a liveness limit, not a safety one. A tab whose database handle can no longer commit (EVS-PRD-event-log/E) stops its delivery cycle and releases the lock, so another visible tab drains. Web Locks exist only in a secure context; on a page without them a delivery cycle refuses to start with a configuration error. Within one isolate a second delivery cycle for the same database is a programming error and is refused: the refusal is keyed by what the backend excludes on, on Postgres the database (two backends in one isolate on one database collide) and on Sembast the open database handle (two backends over one Sembast `Database` collide), while two distinct databases each run their own cycle; two distinct Sembast databases opened over one browser database in one page are excluded by the browser's lock exactly as two tabs are. The assertion bounds who commits queue changes, not who has a send on the wire: a send that a drainer started before it lost the database can still complete after the next drainer's sends. That late send is the residual of assertion J's exception; the fencing of EVS-DEV-destination-drain-lock/B keeps its outcome from being recorded. Delivery uses the destinations registered in the draining process, so every process that may drain registers the same destinations. Other processes' events and halt requests reach the drainer at its next pass, which requires the draining process to have CPU while it serves no request.

**Why dynamic registration?** A user of a running deployment starts sharing data with a new downstream consumer after the deployment has been operating for some time. Adding that consumer's destination at that point must work without restarting the deployment or invalidating its log. The same property supports linking and unlinking destinations as the set of downstream consumers changes.
