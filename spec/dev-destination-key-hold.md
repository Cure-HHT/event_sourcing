# EVS-DEV-destination-key-hold: Key-scoped holds on a destination queue

**Level**: DEV | **Status**: Active | **Implements**: -
**Refines**: EVS-DEV-destination-drain, EVS-PRD-destination-key-hold, EVS-PRD-destinations

## Purpose

This requirement holds the mechanics by which a keyed destination holds one key's events out of its queue and releases them: the block key the fill evaluates and stores on each queue item, the hold transaction a key-scoped permanent failure commits, the routing of a listed key's events on every enqueue path, the release an operator requests by hold id and the fill performs, the release's failures, a recovery's handling of released items, the hold, release and clearing events with their data keys, and the delivery-status read inside a caller's transaction. A block key is the value a keyed destination computes for each event, naming the subject whose events must stay in order. A key list is the per-destination, per-key record that holds the events of a held key out of the queue, in sequence order, each event once, in state held or releasing, under the hold id of the hold event that opened or last re-opened it. One rule carries every assertion: while a key has a key list, none of that key's events enters the queue except by the list's release, in sequence order.

## Assertions

A. Where a destination declares itself keyed, the fill, every replay and every release SHALL evaluate the block key of each event they enqueue or route, outside the fill's transaction, and the fill and every replay SHALL store it on the queue item that carries the event.

B. The fill and every replay SHALL enqueue in one queue item only events of one block key, no block key counting as one.

C. Where a destination does not declare itself keyed, the library SHALL enqueue every queue item of that destination with no block key.

D. The fill and every replay SHALL enqueue with no block key an event whose block key contains `|`.

E. The destination registry SHALL refuse, writing nothing but the registry check record, to register a destination that declares itself both keyed and natively serializing.

F. The fill and every replay SHALL treat a failure of the block-key evaluation on an event as a failure of the destination's transform on that event.

G. When an attempt on a pending head whose block key is K reports a permanent failure scoped to its block key, while every pending item of the destination carries a block key, the drainer SHALL, in one transaction under the drain lock, record the attempt, tombstone the head, delete K's pending items behind it, set K's key list to the events of the head, of the deleted items and of K's existing list, merged in sequence order with each event once, in state held under a new hold id, and append the hold event.

H. If an attempt reports a permanent failure scoped to its item's block key on a head that carries no block key, or while a pending item of the destination carries no block key, then the drainer SHALL wedge the head with cause `permanent_refusal`.

I. The drainer SHALL record on each attempt that reports a permanent failure whether the failure was scoped to the item's block key.

J. A hold SHALL append a `system.destination_held` event whose data carries exactly these keys: `id` (the destination); `database_id`; `key` (the block key); `hold_id` (the new hold id); `row_id` (the tombstoned queue item, or null for a hold that a release failure opens); `failed_event_id` (the event a release failed to build, or null for a hold that tombstones a queue item); `event_ids` (the key list's events, in sequence order); `cause` (`permanent_refusal` or `transform_failed`); and `attempt_count` (the attempts recorded on the tombstoned item, the final one included, or the release failures recorded for the key).

K. While a key has a key list, the fill and every replay SHALL insert each event of that key into the list at its sequence position, untransformed, instead of enqueuing it, and SHALL skip an event the list already holds.

L. A release SHALL refuse, writing nothing but the registry check record, a key that has no key list, and a hold id other than the hold id of the key's list.

M. A release naming the hold id of a key list in state held SHALL, in one transaction, move the list to state releasing and append a `system.destination_hold_released` event whose initiator is the release's initiator and whose data carries exactly `id`, `database_id`, `key`, `hold_id` and `request_id` (the caller's request id).

N. A release naming the hold id of a key list already in state releasing under that hold id SHALL change nothing but the registry check record and return the release event the earlier release appended.

O. While a key list is in state releasing, the fill SHALL release from the list's front only events whose sequence number is at or below the fill position, and only while the destination holds no replay request, transforming them, enqueuing them at the queue's tail and removing exactly those events from the list in one transaction.

P. Every queue item a release enqueues SHALL record the hold id of the list it was released from, and every other queue item SHALL record no hold id.

Q. In the transaction that empties a key list in state releasing, the fill SHALL remove the list and append a `system.destination_hold_cleared` event whose data carries exactly `id`, `database_id`, `key` and `hold_id`.

R. The library SHALL append at most one `system.destination_hold_cleared` event for each hold id.

S. A release SHALL enqueue a key list's events whatever the destination's schedule window, a dormant or ended destination included.

T. When the destination's transform or its block-key evaluation fails on the events a release would enqueue next, the fill SHALL record the failure in that key's release failure record, retry at later passes under the destination's retry curve, and, once the record has spent the retry budget, return the key list to state held under a new hold id with cause `transform_failed`, append its hold event and remove the record, in one transaction that leaves the destination's queue items and wedge record unchanged.

U. An operator recovery SHALL return each event of a removed item that records a hold id to its block key's list at its sequence position, keeping an existing list's state and hold id, and creating a missing list in state releasing under the hold id the item records.

V. Wedging a queue head and honouring a halt request SHALL leave every key list and every release failure record unchanged.

W. The library SHALL offer the delivery-status read inside a caller's transaction, reading from that transaction the records the standalone read returns.

## Rationale

**Why one rule for a keyed destination (assertions A to W)?** A destination's queue is one FIFO with one item in flight, so a definitive refusal of one subject's item, for a cause only that subject's casebook can fix, would otherwise stop every subject's delivery behind it. A keyed destination names, for each event, the subject whose events must stay in order (its block key), and the library holds back that key alone. One rule carries every mechanic: while a key has a key list, none of that key's events enters the queue except by the list's release, in sequence order. Keeping a held key's items out of the queue, rather than leaving a key-scoped wedged item inside it, leaves the head rule, the send fence, halt requests, the start-date check, the recovery and the destination-wedges view with their single-wedge meaning: the queue never holds an item that waits on a hold. A destination that does not declare itself keyed enqueues every item with no block key (assertion C), so nothing a hold adds can touch it, and it behaves exactly as it did before keys existed.

**Why evaluate the key beside the transform, never mix keys, and fall back on `|` (assertions A, B, D and F)?** The block key is consumer code, like the transform, so it runs where the transform runs: outside the fill's transaction (`EVS-DEV-destination-drain/G`), and on every path that enqueues or routes an event -- the fill, the gap, historical and first-activation replays, the re-walk after a recovery, and a release -- so that no path can queue an event of a held key. The key is stored on the queue item, so the hold, a restart and the guard read the decision the fill made rather than evaluating consumer code again. An item carries events of one key only, so a hold takes whole items out of the queue and never splits one. A key containing `|` cannot be told apart in the holds view's row key, which joins the database identity, the destination and the key with `|`, as the destination-wedges view joins its own (`EVS-DEV-destination-drain/K`); the fill queues such an event as a keyless item rather than throwing, which keeps the event in order and makes a refusal of it a destination wedge (assertion H). A failure of the key's evaluation is a failure to build the item and follows the transform's failure path (`EVS-DEV-destination-drain/Y` in the fill and the gap, historical and first-activation replays, which record it in the transform failure record and retry it under the same curve, rather than retrying it silently with nothing written; assertion T in a release).

**Why refuse a keyed destination that serializes natively (assertion E)?** A natively serializing destination is a delivery channel, whose receiver checks that deliveries arrive in one numbered, linked sequence of the sender's events (`EVS-PRD-delivery-channel`). Holding one key's events back and delivering them later would break that sequence and make the receiver refuse every later delivery, and a channel's resume and new generation sweep the queue in ways a key list does not follow. Registration refuses the combination before anything is written but the check record.

**Why the hold transaction, and why a keyless item makes it a wedge (assertions G to J)?** The hold runs in the drainer's attempt transaction under the drain lock, which the fill also takes, so no fill commits between the hold's read of K's pending items and their deletion, and none of K's items is left in the queue behind the hold. The head is tombstoned in a statement of its own after the attempt is appended, because the Postgres guard refuses an attempt append and a status change in one update; its attempts are kept, as on every pending item that is tombstoned (`EVS-DEV-destination-drain/B`). K's pending items behind it carry no attempts, so they are deleted, and their events join the list. The new list merges the head's events, the deleted items' events and any events already in K's list, in sequence order and each once, so a re-hold during a release keeps the remaining list behind the items the release had requeued, and a later release delivers them in their original order. When the head has no key, or any pending item has none, the library cannot tell which subject a keyless item belongs to, and holding K could let a keyless event of K's subject pass a held one; the failure therefore wedges the destination (assertion H), as every refusal did before keys. A spent retry budget, a halt request, a transform-failed head and an acceptance with no receiver record stay destination-wide: none is a statement by the receiver about one key. The attempt records whether its failure was key-scoped (assertion I), so the status derivation at the start of a pass, after a restart or after an attempt committed alone (`EVS-DEV-destination-drain/C` and `EVS-DEV-destination-drain/J`), reaches the decision the drainer reached when it recorded the attempt. The hold event's fields (assertion J) identify the database, destination, key and hold, the item the hold took out of the queue and every event it holds, and the cause and count behind the decision, as the wedge event does for a wedge (`EVS-DEV-destination-drain/I`); a hold that a release failure opens has no queue item, so it names the event the release could not build instead, and every reader of `row_id` handles null.

**Why route every enqueue path, and skip a listed event (assertion K)?** An event of a held key that entered the queue would be delivered ahead of the key's held events, breaking that subject's order. Every path that would enqueue it -- the fill, every replay and the start-date move that requests one -- therefore inserts it into the key's list at its sequence position instead. A routed event is not transformed: the release builds it, so a transform failure of a listed key's event never puts a transform-failed item for that key in the queue (that failure is the release's, assertion T). The list holds each event once, so a re-walk after a recovery, or a replay over a range the list already holds, queues nothing twice. The key lists are part of the state the fill's transaction compares (`EVS-DEV-destination-drain/G`), so a fill computed before a hold or a release commits nothing.

**Why a compare-and-set release that waits for the fill position (assertions L to S)?** An operator releases the hold an event named, by its hold id, so a release decided on a stale reading -- the key held again since, under a new hold id -- is refused, and a repeated request for the same hold, by a retrying caller, changes nothing and returns the event the first one appended. The release moves the list to releasing; the fill does the work, because only the drainer enqueues (`EVS-DEV-destination-drain/E`) and only the drainer's configuration builds items. It takes events from the list's front, only those at or below the fill position and only while no replay request is pending, because a recovery's re-walk or a gap replay may still route an older event of K into the list ahead of its front; releasing past that point would let the older event fall behind a newer one of its key. Each release step transforms the next events, enqueues them at the tail and removes exactly those from the list in one transaction, so a crash between steps neither loses nor repeats an event, and events of K arriving meanwhile join the list's end by routing. Each released item records the hold it was released under (assertion P), which a recovery reads to return it (assertion U). The list is removed, with a clearing event, in the transaction that empties it; at most one clearing event is appended per hold (assertion R), so a list that a recovery re-creates under a hold already cleared ends without a second one. A release ignores the destination's window (assertion S): its events were admitted when first filled, and a destination made dormant or ended since does not strand a subject's held events.

**Why a release failure holds the key again instead of wedging (assertion T)?** A release builds items from events the fill never transformed, so a transform failure there concerns one key's events. It keeps a release failure record per key, timed and spent like the fill's transform failure record (`EVS-DEV-destination-retry-budget`), and once the budget is spent the list returns to held, under a new hold id and with cause `transform_failed`, so an operator sees the key held again and the other keys keep delivering. The re-opened hold has no queue item, so its event carries a null `row_id` and the event it failed to build.

**Why a recovery returns released items to their lists (assertion U)?** A recovery removes the wedged head and every item behind it, released items among them, and re-walks from the rewound fill position. A released event, though, was admitted by a fill long ago, and the rewind is computed from the remaining items only; were it lowered to a released item's events it would re-send every key's events from that point. The recovery therefore returns each released item's events to its key's list, at sequence position, where the next release puts them back in order, and rewinds only for the items no release enqueued (`EVS-DEV-destination-drain/F`). An existing list keeps its state and hold id, since a list already held must stay held; a list the release had emptied and removed is created again in releasing under the hold id the item recorded, so delivery of those events resumes without another operator release. When every removed item was a released one, nothing is left to re-walk and the fill position stays where it was; gap- and historical-replay items and keyless items still count in the rewind, so none of their events is lost. The re-walk routes listed keys' events by assertion K, skipping those already listed, so no event is queued twice and no released event falls behind a later one of its key. Deletion removes the lists instead (`EVS-DEV-destination-drain/A`), since nothing will deliver them.

**Why wedges and halts leave key lists alone (assertion V)?** A destination wedge stops every key, held or not, and its recovery is an operator's; a halt request is a request to stop the whole destination. Neither says anything about a key's held events, so both leave the key lists and release failure records as they are, and the lists resume releasing once the destination delivers again.

**Why read the delivery status inside a caller's transaction (assertion W)?** A consumer that decides a release inside a transaction of its own reads the key lists there; a read transaction of the library's own would wait on the caller's, which holds the same storage. The in-transaction read returns the records the standalone read does (`EVS-DEV-destination-drain/T`), from the caller's transaction.
