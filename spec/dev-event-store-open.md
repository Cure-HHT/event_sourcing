# EVS-DEV-event-store-open: EventStore.open boot flow

**Level**: DEV | **Status**: Active | **Implements**: -
**Refines**: EVS-PRD-event-log

## Purpose

How the substrate realizes the EVS-PRD-event-log obligations at construction time. `EventStore.open` is the single entry point production code uses to obtain a usable `EventStore` instance. It opens the storage from the description the application supplies, or takes a backend that the description names as application-supplied (EVS-DEV-storage-capability), and keeps the backend to itself. The private `EventStore._` constructor is not exposed, and `EventStore.openForTest` is for tests: it refuses in a build with assertions disabled. Before its boot, open registers the build's data generation with the incompatible-generation guard, which refuses a conflicting live instance before anything is written (EVS-DEV-version-compatibility/F). Open then runs its whole boot in one storage transaction, under the guard's boot lock, before serving subscribers. It first decides whether this build may open the database -- the database identity, the data format recorded by the latest library-version event the database appended itself and by the database's generation record, and the entry-type majors stored for its views and in that record -- and refuses before writing anything. When it accepts, it appends the library-version event that records this build's package version and data-format version, and the registry audit, when each is due, then seeds `view_target_versions`, raises the stored target of every lagging (view, entry type) pair and records a promotion gap for it, records a catch-up gap for every view it seeds over an existing log, merges its generation into the record, and writes a boot record. The boot re-derives no view row: the views it finds behind are re-derived after the open returns (EVS-DEV-view-convergence). Throughout, it reports its progress to an observer the caller may supply, which observes and decides nothing.

## Assertions

A. The substrate SHALL expose `EventStore.open(...)` as the sole constructor of `EventStore` instances for production code; the private constructor `EventStore._` SHALL NOT be reachable from outside the library; and `EventStore.openForTest(...)`, the test-only constructor, SHALL be annotated so that the analyzer reports a call from production code, SHALL apply the refusals of `EventStore.open`, and SHALL append no library-version event.

B. `EventStore.open` SHALL append `lib_version_initialized` when the database holds no locally appended library-version event.

C. `EventStore.open` SHALL append `lib_version_changed` when its package version or its data-format version differs from the one recorded in the latest locally appended library-version event, including when it is older.

D. `EventStore.open` SHALL record the library's package version and data-format version in every library-version event it appends, and SHALL refuse, throwing `DataFormatIncompatibleError` before any write, to open a database whose latest locally recorded data-format major, or whose recorded data generation's data-format major, differs from its own, unless the generation guard has already refused the open because a live instance holds a conflicting generation, or the open has already been refused, with a reason of its own, because an earlier data format wrote the database.

E. `EventStore.open` SHALL perform its boot in one storage transaction, deciding every refusal (database identity, data format, entry-type downgrade) before its first write, and then appending any library-version event and any registry audit event before seeding view target versions and recording convergence gaps; an accepted boot SHALL write in that transaction even when no event, seeding or gap is due.

F. At the first open, `EventStore.open` SHALL mint a database identity, or adopt one already stored, and record it in the initialization event; at every later open it SHALL refuse, before writing anything, when the stored identity is missing or differs from the identity recorded in the database's earliest locally appended initialization event, and SHALL refuse with a distinct reason, before writing anything, a database that an earlier data format wrote: one whose locally appended library-version events record no identity or no data format, whose log records locally appended library-version changes but no initialization, or whose stored events or view target versions are in an earlier data format's shape. An event is locally appended when it carries no receiver provenance entry.

G. `EventStore.open` SHALL report the progress of its boot to an observer the caller may supply: the phase the boot is in (its checks, and its completion) and the time since the open began.

H. <RETIRED> The progress of re-deriving views is reported by view convergence (EVS-DEV-view-convergence-scheduling).

I. `EventStore.open` SHALL report the completion of its boot only after the boot transaction has committed, so that a refused open reports no completion.

J. When the backend runs the boot transaction again, `EventStore.open` SHALL report the phases of the new run again, starting from its checks.

K. `EventStore.open` SHALL NOT await a future its boot progress observer returns.

L. `EventStore.open` SHALL log what its boot progress observer, or work the observer started in its zone, throws, and SHALL continue the boot.

M. `EventStore.open` SHALL refuse with `StateError` every call that its boot progress observer, or work the observer started in its zone, makes while the boot runs to open an event store, to run a transaction of an event store or `rebuildView`, or to start a transaction on a storage backend the library ships.

N. The boot transaction of `EventStore.open` SHALL read, write and delete no view row.

O. The boot transaction of `EventStore.open` SHALL read no event other than the library-version events, the registry audit events and the latest event of the log.

## Rationale

**Why a single boot entry point?** A two-step construction pattern (raw constructor + post-init `open()` call) would leave intermediate states where the store is partially initialized -- accepting subscribers before library-version events have been emitted, or before compatibility has been checked. Making `open` the only path eliminates those windows.

**Why one transaction?** A refusal decided after a committed library-version event would leave the log recording a version that never opened the database. Deciding every refusal before the first write, inside the transaction that then writes, means a refused open writes nothing and an accepted one records exactly what it did. The boot reads the log inside that transaction, so two concurrent first opens (instances of one revision, a canary beside the serving revision, two browser tabs) decide on each other's commits and record one identity and one initialization, and concurrent opens of one build that changes the recorded version record one change. A storage backend may run the body more than once (a serialization retry, or a browser database re-running it after another tab committed); each run decides again from what it reads, so the boot stays restartable, and a crash at any point leaves the database as it was before the open.

**Why the library-version event first?** The library-version event records which build opened the database at sequence N. The registry audit follows it in the same transaction, recording the entry-type versions and declarations the build opened with. Appending both before seeding and gap recording puts every `view_snapshot_promoted` audit, which the transaction completing a promotion appends after the open, after the version change that caused it, so a reader replaying from genesis sees the version change, then the promotions it triggered.

**Why does the boot lock the sequence counter's table first?** On a database whose transactions contend (Postgres, serializable), a boot beside a serving revision competes with that revision's appends, which all update the sequence counter, and with its view convergence, which writes the pair records the boot reads. A boot that read first and locked later would be aborted by every such write that committed meanwhile, and a steadily appending revision could starve it; so would a boot whose first statement locked the counter row itself, because that statement already fixes the boot's snapshot, and a row changed while the boot waited for it aborts the boot. The boot's first statement therefore locks the table holding the counter, a statement that fixes no snapshot. Every append writes that table and every convergence transaction locks it first in the same mode (EVS-DEV-view-convergence-scheduling/C), so the lock waits for all of them in flight to commit, the boot's snapshot then includes them, and later ones wait for the boot to commit, after which each fails at most once and succeeds on its retry. Two boots on one database run one after the other, as the generation guard's boot lock already orders them. The cost is that the serving revision's appends, and every other write to that table, pause for the boot transaction's whole duration: its reads of the library-version events, the registry audit events, the latest event and the stored targets and gaps, its checks, and its seeding and gap recording, a constant amount of work per registered view and (view, entry type) pair. It re-derives no view row and reads no other event (assertions N and O): the views the boot finds behind are re-derived after the open returns, in transactions bounded in time (EVS-DEV-view-convergence, EVS-DEV-view-convergence-scheduling). On Postgres the library-version and registry audit events are found through an index on event type, so the pause does not grow with the log; on Sembast they are found by filtering the event store in memory, a scan that grows with the log but is far cheaper than a fold. On Postgres `bootLockWait` bounds how long another instance's open waits for the boot lock, which a boot holds for its whole duration. A browser database shared by several tabs has the same contention in another form: a tab whose commit another tab preceded re-runs its transaction on fresh data, so a tab appending steadily would make another tab's boot re-run without end. There every tab's transactions take the database's write lock shared and the boot takes it exclusively, so the boot waits for the writes in progress and the later writes wait for the boot, as the Postgres table lock orders them. Opening a backend runs no schema statement; provisioning, which does, runs as a separate step under the same boot lock (EVS-DEV-postgres-backend/G).

**Why does an accepted boot always write?** On a multi-tab browser database, a transaction is checked against other tabs' commits only when it writes, and is then re-run on fresh data if another tab committed first. The boot record makes every accepted boot such a transaction, so an acceptance is never decided on a stale view of the database. A refusal writes nothing: what it compares only moves one way (a recorded data-format major and a stored entry-type major never fall), so a refusal decided on an older view is also the decision on the newest.

**Why does compatibility, not version order, decide?** Redeploying a prior release is a required operation, and a no-traffic canary overlaps the serving revision on one database. Builds of one data-format major read and write the same stored shapes, so an older build of the same major opens a database a newer one opened, and records that it did. A build of another data-format major is refused: an older build cannot read a newer major, and a newer build has no reader for an older one. A major bump is therefore a stop-then-start deployment -- every instance of the old revision stops before the first instance of the new one opens the database -- and recovery after it is a restore from a backup taken before the switch, or a roll-forward. No override exists: an open the library does not record would break the guarantee that the log states which versions opened the database. `EventStore.openForTest` is such an open -- it records no library-version event, so tests keep predictable sequence numbers -- and it is confined to tests by the analyzer, which reports a call from production code (assertion A); the guarantee holds for `EventStore.open`.

**Why also a generation record and a live guard (assertion D)?** The latest library-version event covers the data format of every build that opened the database with `EventStore.open`. The generation record covers every boot that committed, `openForTest` included, and every registered entry type's major, including one no view names; and the live guard covers an instance that is running now. Each refuses with its own exception: a live conflict throws `IncompatibleGenerationException` before the boot transaction starts, and a durable refusal is decided inside it, the data format before the entry types, so the same scenario throws the same exception on every backend.

**Why record every open by a different version?** The log then states which versions opened the database, and in what order. It records each open, not which of two running builds appended a given event: while builds of one data-format major run side by side, the latest library-version event before event N names the last open, not the build that appended N. The closed-under-events claim -- state under the library's conventions is reconstructable from the log -- is therefore a claim about the views of the build that re-derived them: two builds of one major may fold different view rows during an overlap (EVS-DEV-version-compatibility/E, L), and a view equals a replay of the log under the definitions of a build that registers it once that build has re-derived it, at its open or with `rebuildView`.

**Why report the boot's progress, and why may the observer only observe (assertions G and I to M)?** An open waits for the generation guard's boot lock while another instance boots or a provisioning runs, and on Postgres for the appends and convergence transactions holding the sequence counter's table. A platform that sees no sign of life from a starting process may kill it; the killed boot rolls back, and every retry waits again. Progress lets a deployment answer a liveness probe as soon as the process runs and a readiness probe with the phase the boot is in, so a boot waiting for its locks is waited for rather than restarted. The progress of re-deriving views after the open is reported per view by view convergence (EVS-DEV-view-convergence-scheduling/N). The completion is reported after the boot transaction commits, because a run the backend discards and runs again has not completed; between a discarded run and the next one the discarded run's last report stands.

The observer is application code, and the library does not let application code take part in what the boot decides: the outcome of an open follows from the database and the build alone, so the observer adds no trusted input. The boot calls it synchronously and does not await what it returns, so its synchronous work extends the boot -- on Postgres, the time every append to the database is held back -- and it must return quickly. What it throws is logged: it runs in an error zone the library owns, which outlives the boot, so an error its later work raises is logged there too and does not reach the caller's zone, and a future created in that zone that fails does not complete an await in another error zone. The refusal is a uniform rule that the observer only records: a call from it into the library's storage would at best queue behind the boot or run beside it, where a view write on Postgres can make the boot run again and pause appends again, so it is refused at once, naming the rule, for every event store and backend whichever database they are over. The observer's zone marks the calls it and its work make; a callback it hands to code registered outside that zone (a stream listener subscribed elsewhere, a continuation registered elsewhere, work run in the root zone) is not recognised, nor is a read a backend serves outside a transaction, nor a transaction an application-supplied backend starts.

**Why a database identity, and why only local events?** A database identity names the database independently of the installation or process that opens it, so every event store over one database agrees on it. It is minted once and recorded in the initialization event; the stored copy is checked against that record at every open, so a storage that lost or changed the record the library wrote -- a durability failure, a restore that mixed two databases, tampering -- is refused rather than silently given a new identity. A database that ingests from peers holds their library-version events too, including newer builds' and other identities'. Only events the database appended itself describe it: ingest adds a receiver provenance entry to every event it stores and the library's own appends carry none, so the boot reads only events without one, and a peer cannot forge that property away.

**Why refuse a database with no identity or no data format?** Such a database was written by a build that predates this data format, as is one whose log holds library-version changes but no initialization, or whose stored events or view target versions carry an earlier format's version fields. There is no migration from those builds; the database must be reset, and the refusal says so by name before anything is written rather than failing later on an unreadable shape.
